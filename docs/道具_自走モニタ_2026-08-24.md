# 道具: 自走モニタ(2026-08-24 起票)

**利用者指示(2026-08-24)**:

> 今このプロジェクト配下の自動実行が動いているか・どのくらい進んでいるか・
> どういう状況なのかを一目で確認できる GUI を作る。パラメーター各種と、
> 各種評価値は裁定でも必要。修正のたびに対応させる必要が可能な限り少なく
> なるように。AI を消費しない機械的動作を行う。このプロジェクトの AI が
> 現状を Monitor しているか≒作業の進行時に自動で次の行動ができる状態に
> なっているかも判別したい。時間のかかる計算を開始したあと、その結果を
> 待つふりをして待っていないことが多々あるので。

## 使い方

```bash
npm run monitor      # http://127.0.0.1:7420 が開く(端末を占有する)
```

端末を閉じても残したいとき(常駐・二重起動しない):

```powershell
powershell -ExecutionPolicy Bypass -File scripts\monitor.ps1
```

- 依存ゼロ(node の標準モジュールのみ)。**AI は一切関与しない。**
- 5 秒ごとに自動更新。ブラウザのタブ名が状態を表す(`● 計算中 …` / `■ 投げっぱなし …`)。
- ブラウザを開きたくない: `EXOCLIM_MONITOR_OPEN=0 npm run monitor`
- 港を変える: `EXOCLIM_MONITOR_PORT=7500 npm run monitor`
- 実装: [scripts/monitor_server.mjs](../scripts/monitor_server.mjs)(収集と判定)、
  [scripts/monitor_ui.html](../scripts/monitor_ui.html)(表示)、
  [scripts/monitor.ps1](../scripts/monitor.ps1)(常駐起動)。
  判定の要は [tests/unit/scripts/monitor_judge.test.ts](../tests/unit/scripts/monitor_judge.test.ts) で固定。

## 「AI が監視しているか」の判定(この道具の中核)

自走の生死は**口先では判定できない**。「待っています」と書いたセッションが
実は end_turn していた、というのが前任 2 名の死因([教訓 §11](教訓.md))。
だから根拠を**ハーネス自身の記録**に置く。

### 何を読むか(2026-08-24 に実データで確認した語彙)

**追跡が始まる形**(いずれも tool_result の**先頭**に現れる):

| 文言 | 出す道具 | 解けるまで |
| --- | --- | --- |
| `Command running in background with ID: <id>` | Bash / PowerShell を `run_in_background` で | 完了通知 |
| `Monitor started (task <id>, persistent — …)` | Monitor | TaskStop かセッション終了 |
| `Workflow launched in background. Task ID: <id>` | Workflow | 完了通知 |
| `Async agent launched successfully … agentId: <id>` | Agent | 完了通知 |

**追跡が解ける形**(`queue-operation` と user メッセージの両方に同じものが載る):

```
<task-notification><task-id>X</task-id> … <status>completed|failed</status> …
```

**解けない形** — 見張りの発火には `<status>` が無い:

```
<task-notification><task-id>X</task-id><summary>Monitor event: "…"</summary><event>…</event>
```

見張りは撃っても生き続ける。**撃つたびに AI が起こされる**ので、
見張りが 1 つ生きていれば、そのセッションは冷えていない。

### 判定の骨格

> **問いは「この計算に札が付いているか」ではなく、
> 「この計算を抱えているセッションが armed か」。**

1. 会話ログから、**開始が記録され終了通知が来ていない追跡**(= 生きている追跡)を数える。
2. 走っている計算を、**起動時に AI が打ったコマンドの原文**で持ち主のセッションへ結びつける。
   文字列照合なので、切り離し起動(PowerShell の `Start-Process` 等)でも辿れる。
3. 持ち主に生きている追跡があれば **見守られている**。無ければ **投げっぱなし**。
   持ち主を特定できず、しかし armed なセッションが居るなら **判定不能**(狼少年にしない)。
4. 追跡の開始時刻と OS プロセスの誕生時刻はほぼ一致する(実測 0.1 秒差)ので、
   対応するプロセスが居ない追跡は**死んだ見張り**として armed に数えない。

### 使ってはいけない根拠(2026-08-24 に 2 回踏んだ)

**(1) 札(`tasks/*.output`)の時刻。**
札は「**最初の出力が出た時刻**」に作られる。30 分なにも出力しない見張りでは
札の誕生が 30 分遅れる。実例: v33 較正の見張りは 17:21:39 に起動したが、
札 `b9o4affff.output` が生まれたのは最初の進捗が出た 17:51。
「札の誕生 ≒ ジョブ起動」と仮定した初版は、**正しく運用しているスレを
「投げっぱなし」と誤報した**。札は画面に出すだけで、判定には使わない。

**(2) 文字列が現れたこと。**
`Command running in background with ID: …` は、**ログを grep した出力**として
tool_result に平気で現れる。実際、この道具を作っている最中に自分の grep 出力を
読んで「追跡 4 件」と誤検知した。よって
 ・行頭に錨を打つ
 ・**その結果を返した道具の種類まで照合する**(`run_in_background` が真か、
   `Monitor`/`Workflow`/`Agent` か)
 ・出力先の道が自分のセッション ID を指しているか
の 3 つで守る。

### 出る判定

| 表示 | 意味 | 何をすべきか |
| --- | --- | --- |
| 計算中 — 見守られている | 持ち主に生きている追跡がある | 待ってよい |
| 計算中 — 投げっぱなし | 起こす者が居ない | AI に拾わせる |
| 計算中 — 起動元を特定できない | 判定不能。armed なセッションは居る | 画面の根拠を見て自分で判断 |
| **結果は出ているのに AI はまだ知らない** | 成果物は確定したが持ち主が黙っている。見張りの次の点検までの時間も出す | 急ぐなら声をかける |
| 計算は終わっているのに AI が反応していない | 追跡が AI の最終発話より後に書かれ、計算は無い | 起こす |
| 二重起動 | 同じ出力を取り合っている | 片方を殺す |
| 裁定待ち / 停止札 / 静止中 | それぞれの札のとおり | — |

見張りのコマンドに `sleep N` があれば**点検間隔として読み取り**、
「次の点検まであと何分」を出す。30 分間隔の見張りなら、計算が終わっても
AI が気づくのは最大 30 分後 — それが見えないと「壊れている」と誤解する。

### 実例(この道具が実際に捕まえたもの)

- **前景実行の孤児化**(初日): `diag_dead_constants.ts` を前景で起動して
  ツールが時間切れになり、プロセスだけが残っていた。二重起動でもあった。
- **誤報**(初日): v33 較正(切り離し起動 + Monitor 見張り)を
  「投げっぱなし」と誤判定。上の (1) が原因。規則を作り直した。
- **引用の誤読**(初日): 自分の grep 出力を追跡と誤読。上の (2) が原因。

## 修正への追従を最小にする作り(重要)

**この道具はスキーマを持たない。** 「どこを見るか」だけを書き、
「何という指標があるか」は書いていない。

- **評価値** — `report.json` を丸ごと汎用ツリーで出す。指標が増えれば勝手に出る。
  見出しのタイルへ昇格させたいものだけ `CFG.headline` に 1 行足す
  (パスが無ければ黙って飛ばすので、消えた指標で壊れない)。
- **パラメータ** — `best_*.json` の全キーを出し、`SPACE` の正規表現解析で
  下限・上限を当てる。定数が増減しても直さない。
- **推移** — `log_*.jsonl` の各行から**半数以上の行に現れる数値キー**を
  自動で見つけて系列にする。新しい指標を吐けば勝手にグラフの選択肢に出る。
- **run** — `log_<名>.jsonl` / `state_<名>.json` / `best_<名>.json` /
  `run_<名>.meta.json` の命名から run 名を自動発見する。v34 を始めれば勝手に出る。
- **追跡の語彙** — ハーネスが返す文言に依存する唯一の箇所。ここが変わったら
  `scripts/monitor_transcript.mjs` の `ARMINGS` を直す。壊れると
  「追跡ゼロ」に倒れる = 狼少年になるので、静かな誤りにはならない。
- **進捗** — `state` に `cursor` と `screenCursor` があれば進捗率にする。
  無ければ進捗バーを出さないだけ。

書式が変わって読めなくなった箇所は、黙って空にせず画面に警告を出す
(`SPACE` が読めない / 台帳の項目が 0 件)。

### 直す必要があるのはここだけ

| 変えたもの | 直す場所 |
| --- | --- |
| `optimize_lib.ts` の `SPACE` の書式そのもの | `parseSpace()` の正規表現 |
| 積み残し台帳の項目の書式 | `collectLedger()` の正規表現 |
| 出力先ディレクトリ(`out/optimize` 等) | `CFG` の先頭 |
| 見出しに出したい評価値 | `CFG.headline` に 1 行 |
| 新しい種類のスクリプト分類 | `CFG.procKinds`(スクリプト名にだけ当てる) |
| ハーネスの追跡の文言 | `monitor_transcript.mjs` の `ARMINGS`(道具の種類も併記) |

## 既知の限界

- **会話ログを末尾からしか読まない。** 初回は 4MB(実測: 忙しいセッションで
  約 90 時間ぶん)。それより古い追跡の開始は見えない。末尾しか読めていない
  セッションは画面にその旨を出す。2 回目以降は増えた分だけ読む(1〜2ms)。
- セッションが `/clear` されたり端末が閉じられていると、会話ログ上は追跡が
  残る。見張り・背景ジョブは OS プロセスの有無で死活を見るが、
  Workflow と Agent は本体の中で動くので外から確かめられない。
- 起動コマンドの原文が読み取り範囲の外にあると、持ち主を特定できない。
  そのときは「判定不能」と出す(投げっぱなしとは言わない)。
- 利用者が端末で直に起動した計算は、どのセッションにも紐づかない。
  armed なセッションが居なければ「投げっぱなし」と出るが、これは
  「AI は起こされない」という意味では正しい。
- プロセス一覧は PowerShell の `Get-CimInstance` を 3 秒キャッシュで叩く。
  1 回あたり 1 秒弱。相対パスで起動したプロセス(`node scripts/x.mjs` を
  リポジトリ内から)はコマンド行に `ExoClim-3` を含まないので見えない。
