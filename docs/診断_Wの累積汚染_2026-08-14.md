# 診断: 掃引の W は累積平均だった — 段 20 の看板の数字は無効

日付: 2026-08-14
発見: 前任セッションの引き継ぎ点検中(コード読みのみ、計算なし)
影響: [実験記録_凝結率の幅](実験記録_凝結率の幅_2026-08-14.md) の主結論、
      および commit `3918960`(鋭さ 4 での再較正 v23crh)の前提

## 欠陥

`resetConservativeStats()` は 4 つの診断量を 0 に戻すが、
**`meanWaterMm` と `waterSamples` を戻していなかった**
(`src/sim/step06_precipitation.ts`)。

一方 `scripts/exp_pressure_lever.ts` は、**同一プロセスの `for` ループ**で
レバー値を順に回しながら、各周回の末尾で

```ts
const wMm = CONSERVATIVE_STATS.meanWaterMm / Math.max(1, CONSERVATIVE_STATS.waterSamples);
```

を読んでいた。積算が消えないので、**k 番目に表示された W は、1〜k 番目の
全水準を混ぜた累積平均**である。その水準の値ではない。

単発で測る `scripts/diag_water_vapor.ts` は自前で 0 を代入してから回していた
ので**無傷**。つまり段 20 の発端だった「W = 3.36mm(実物 25mm)、モデルは
7 分の 1 しか水を持っていない」は正しい。**壊れているのは処方の効果のほう。**

## 何が変わるか

積算は `waterSamples++` が**「月 × 結合反復」1 回につき 1 度**走る
(`step06_precipitation.ts` の輸送求解の直後)。結合反復の回数は収束するまで
可変(上限 24)なので、**1 水準あたりのサンプル数は水準ごとに違う**。
よって「等サンプル」を仮定した単純な逆算はできない。区間で押さえる。

鋭さ 0 の真値 W₁ = 3.4(1 番目なので無傷)。鋭さ 4 のサンプル数を
鋭さ 0 の k 倍とすると、表示された 29.1 は

```
29.1 = (W₁ + k·W₄) / (1 + k)   →   W₄ = 29.1 + 25.7/k
```

```
k        1      2      3     →∞
真の W₄  54.8   42.0   37.7   29.1（下限、到達しない）
```

鋭さ 4 は壁時計で 6.2 倍(225s → 1394s)かかっており、その一部は
結合反復の増加ぶんなので **k > 1 が濃厚**。真の W₄ はおそらく **30〜45mm**。

厳密な値は k に依るが、**結論は k に依らない**:

> **k がいくつであっても W₄ > 29.1mm。**
> 累積平均は必ず先行水準に引き下げられるので、真値は表示値より大きい。

したがって鋭さ 4 の W は実物 25mm を**下から着地したのではなく、
上へ通り過ぎている**。表示 328.8 / 462.4 の水準も同様に真値はさらに大きい。

したがって段 20 の看板

> **W が 3.4mm → 29.1mm(実物 約 25mm)。合わせに行っていないのに合いました。**

は成立しない。**着地したのではなく、通り過ぎていた。**

## 波及

1. **利用者への裁定依頼(「物理的に正しいが成績が悪い」)は前提が崩れた。**
   鋭さ 4 は「物理的に正しい」のではなく「行き過ぎ」だった。
   成績が 3.45 落ちたことと矛盾しない。
2. **正解は鋭さ 0 と 4 の間にある。** これは前任が
   「指示がなければ C を測って材料を増やしておきます」と書いて
   **実行しないまま 5.3 時間止まった**選択肢 C そのものである
   ([教訓.md §11](教訓.md))。
3. 再較正 v23crh(鋭さ 4 固定、8 時間)は前提が無効なので停止した。
   別に、1 評価 1714 秒 × 480 分 = **約 17 評価**しか回らず、
   62 定数の探索空間に対して構造的に足りない
   (過去に成果が出た較正は 300〜973 評価)。

## HEAD が壊れていた — 鋭さ 4 は解ではない(2026-08-14、確定)

引き継ぎ点検で `npx vitest run` を回したところ、**159 件中 3 件が失敗**した。
`tests/unit/sim/water_budget.test.ts` の 2 件は次のとおり:

```
× 結合反復が上限に到達せず収束している(診断に記録)   ← 通常の地球で落ちる
× 退化条件(全海・全陸・無降水・高傾斜)で有限かつ収束する
    → 高傾斜: expected false to be true
```

**結合反復が収束していない。しかも地球の標準設定ですら落ちる。**

`crhSuppressionSharpness` を 4 → 0 に戻して同じテストを回すと:

```
鋭さ 4 → 5 件中 2 件が失敗、所要 310 秒
鋭さ 0 → 5 件すべて通過、  所要 116 秒（2.7 倍速い）
```

**因果は確定した。** 段 20 が観測した「費用 6 倍」も、その大半が
未収束による反復の空転だった疑いが濃い(収束すれば 2.7 倍速くなる)。

この失敗は私の変更が原因ではありえない。今回触った `meanWaterMm` /
`waterSamples` は `src/` の中で**書き込まれるだけで一度も読まれない**
(grep 済み)。診断量であって物理に入らない。変更もすべて追加行のみ。

原因は HEAD の定数、すなわち commit `3918960` が有効にした
`crhSuppressionSharpness: 4` + `crhFromWater: 1` と考えるのが自然である。

そして**前任セッションはこの commit の前後でテストを一度も回していない**
(セッションログ中の tool 呼び出しを全走査し、`vitest` / `npm test` の
実行が 0 件であることを確認した)。CLAUDE.md の作法
「機能単位でテストを通してからコミット」が守られていない。

これが正しければ、段 20 の物語はさらに単純になる:

> **鋭さ 4 は「物理的に正しいが成績が悪い設定」ではなく、そもそも解ではない。**
> 元の事前登録の判定 5「輸送と結合反復が収束する(未収束 0)」を満たしておらず、
> **適用範囲外**である。W も v3 も読んではいけない数字だった。

## 直したもの

- `resetConservativeStats()` で `meanWaterMm` / `waterSamples` も 0 にする。
  **根本原因を直す**(掃引側で毎回代入する場当たりにはしない)。
- `scripts/exp_pressure_lever.ts` の各行に**収束の状態**を並べる
  (未収束件数 / virga 未収束 / 最悪残差 / 反復数)。未収束なら
  「この行は適用範囲外」と明記する。前任が
  「掃引の表に未収束の件数を出していなかったのは道具の不備です」と
  自ら書きながら塞がなかった穴。鋭さ 8 の W = 328mm は
  **解ではなく反復の打ち切り**である可能性が高く、それを
  表に「解」として載せていた。

## 教訓

[教訓.md](教訓.md) の「反復の打ち切りが答えを決める」(EBM で 3 件)と
同じ型が、診断量の**積算器**でも起きた。追加の一般則:

> **プロセスをまたいで生き延びる可変状態は、リセット関数に必ず全項目を書く。**
> 新しい項目を足したとき、リセット側を直し忘れると、
> 単発の測定は正しいのに掃引だけが静かに嘘をつく。
