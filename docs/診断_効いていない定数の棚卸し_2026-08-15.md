# 診断: 探索空間 62 定数のうち **4 件が完全に無駄**だった

日付: 2026-08-15
道具: `scripts/diag_dead_constants.ts`(新規)
出力: `out/diag_dead_constants.txt`
前段: [診断_ストーム供給は保存型で死んでいる](診断_ストーム供給は保存型で死んでいる_2026-08-15.md)

## やったこと

`stormMoistureSupply` が保存型で完全に死んでいると分かったので、
**同じものが他にもあるはず**と考え、探索空間の 62 定数を機械的に点検した。

各定数を ±20%(0 のものは範囲の 10%)動かし、2° 格子・EBM 短縮で
パイプラインを回して**降水がビット一致するか**を見る。
教訓 §9「**ビット一致は『頑健』ではなく『独立変数が動いていない』の徴候**」を、
探索空間の全体に対して一括で適用する道具である。

## 結果: 4 件

```
stormMinQRel
stormMoistureSupply
stormMoistureDecayKm
warmHumidSupplyNorm
```

**62 定数の 6.5% が、答えに 1 ビットも影響しない。**

### 内訳は 2 種類

**(1) ストーム供給の一族(3 件)** — 保存型で経路ごと切れている。

`stormSupply` は非保存の降水式にしか入っておらず、保存型の源泉にも
凝結率にも現れない(段 6 の移行漏れ)。
したがって `stormMoistureSupply` だけでなく、その計算に使う
`stormMinQRel`(水蒸気量の下限)と `stormMoistureDecayKm`(海岸からの減衰長)も
**まとめて死んでいる**。

**(2) 親が 0 になった正規化定数(1 件)** — 連鎖して死んでいる。

```ts
const supplyNorm = Math.min(1, supply[i] / K.warmHumidSupplyNorm);
warmHumidF = 1 + K.warmHumidConvectiveBoost * warmth * supplyNorm²;
```

`warmHumidConvectiveBoost` は**較正が 0 まで押し下げた**
([診断_較正が探索空間の端に張り付いている](診断_較正が探索空間の端に張り付いている_2026-08-15.md)
で時系列を確認済み: 0.032 → 0.064 → 0.0208 → 0)。
親が 0 なら `warmHumidF = 1` で固定なので、**正規化定数も効かなくなる**。

**較正は、自分で殺した機構の正規化定数を振り続けていた。**

## 何を意味するか

- **較正の評価が 6.5% 無駄になっていた。** 座標降下は 1 定数ずつ振るので、
  4 定数ぶんの評価(1 巡あたり 8 評価前後)が**必ず空振りする**。
- より重いのは **(1) が「機構の移行漏れ」の指標**であること。
  virga・ストーム供給と、**保存型への移行で落ちた機構が 2 つ見つかった**。
  他にも落ちているものがある可能性は残る
  (この診断は「探索空間にある定数」しか見ないので、
  **探索空間の外の機構は映らない** — 今日 4 件見つけたのはそちら側だった)。

## この診断の限界(道具自身に書いてある)

- **2° で判定している**ので、格子依存で 2° だけ効かない機構は見逃す。
  候補が出たら 1° で確かめること(今回の 4 件は経路が切れているか
  親が 0 なので、格子には依存しない)。
- **降水だけを見ている**ので、気温にしか効かない定数も候補に出うる。
  実際には気温系はすべて「効いている」と出た
  (EBM → 気温 → 飽和量 → 降水 の経路があるため)。
- **「効いている」= 正しく効いている、ではない。**
  今日見つけた `orographicRefSlope`(比 0.05 で 5% しか効かない)のような
  「弱く効いている」ものは、この診断では「効いている」に分類される。

## 次にやること

1. **探索空間から 4 件を外す**(較正の無駄を消す)。
   ただし (1) は「保存型に繋げば効く」ものなので、
   **外すより繋ぐほうが筋**である。繋ぐ設計は
   [診断_ストーム供給は保存型で死んでいる](診断_ストーム供給は保存型で死んでいる_2026-08-15.md)
   に書いた(**単位の設計が要る。水が閉じることを先に保証する**)。
2. `warmHumidSupplyNorm` は親が 0 なので、
   **親を生き返らせるかどうかが先**である。
   `warmHumidConvectiveBoost` は「高温湿潤の陸での対流性増幅」で、
   中位の陸(緯度 30°・12°C)には効かない位置にある。**優先度は低い。**

## 追記(2026-08-16): **判定方法を直して測り直しても、結論は同じだった**

この診断の初版は、降水の合計と最大値を**小数 6 桁に丸めた文字列**で比べていた。
外部監査に「丸めのせいで小さな影響を『効いていない』と誤判定しうる」と
指摘されたので、判定を **全セル全月の最大絶対差**へ直し、
「完全に 0 のときだけ効いていない」とした(`maxAbs === 0`)。

**直した判定で測り直した結果、候補は同じ 4 件のままだった。**

>

> 修正前の 8/15 06:52 のもの)を読んで報告したためである。

> **完了通知を見て、読むファイルの更新時刻を確かめずに開いた。**


丸めの緩さで拾われた偽陽性ではなく、**本当に 1 ビットも動いていない**。
上の (1)(2) の説明(経路が切れている / 親が 0)がそのまま裏付けられた。

監査が「SPACE がストーム 3 定数を探索しているのに配線が切れている」と
指摘したのは**正しい**。私は一度「別系統かもしれない」と疑ったが、
コードを追うと `stormSupply` は非保存の降水式にしか入っておらず、
保存型では `STORM_DIFFUSION.boost = 0`(既定)のとき使い道が無い。
