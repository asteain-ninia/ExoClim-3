# 提案: 目的関数が季節を測っていない(2026-08-02)

**実装していない。判断は利用者に委ねる。**

## きっかけ

数値の欠陥を 3 件直したところ、こうなった:

| | 修正前 | 修正後 |
|---|---:|---:|
| 大分類一致率 | 73.9 | **70.6** |
| 詳細一致率 | 42.7 | **35.7** |
| 季節位相の遅れ(対観測) | 25.3 日 | **22.7 日** |
| 内陸の季節振幅の過大 | +4.32°C | **+3.85°C** |
| 地域ゲート | 13 | **14** |

**採点は下がったのに、観測と直接比べた季節の指標は良くなった。**
この食い違いは偶然ではなく、目的関数の構造から予想できるものだった。

## 現行の目的関数 v2(2026-07-31 凍結)

```
fitness = 大分類% + 1.1×ゲート数 + 0.25×詳細%
          − 0.35×気温**年平均**RMSE − 0.004×降水**年**RMSE
          − 0.02×|陸平均降水の偏差|/10 − 0.3×ITCZ 線 RMSE
```

気温は**年平均**しか見ていない。降水も**年合計**しか見ていない。
つまり **季節振幅と季節位相を一切測っていない**。

一方でケッペンの分類は季節で決まる:

- 第 3 文字 a/b/c/d は**最暖月**気温と 10°C 超の月数
- 第 2 文字 s/w/f は**最少月/最多月**降水
- E は**最暖月** < 10°C

季節を測らない目的関数で、季節で決まる分類の一致率を上げようとしている。
一致率という「粗い量」を通してしか季節に触れていないので、
**季節振幅が実測から離れても一致率が上がる方向**が存在しうる。
実際、未収束の EBM(季節振幅が過大)のほうが一致率は高かった。

## 提案

季節の量を**直接**目的関数に入れる。追加候補(いずれも観測フィクスチャから
そのまま計算でき、新しいデータは要らない):

| 項 | 根拠 |
|---|---|
| 最暖月気温 RMSE | ケッペン第 3 文字と E 判定を直接決める |
| 最寒月気温 RMSE | C/D 境界(最寒月 0°C)を直接決める |
| 最少月降水 RMSE | 第 2 文字 s/w と Af/Am/Aw を直接決める |

年平均 RMSE を置き換えるのではなく**併記**する。年平均は放射収支の、
最暖/最寒月は熱容量と輸送の、それぞれ別の側面を見ている。

重みは「各項の典型的な大きさで無次元化してから等重み」から始めるのが素直。
決めたら**結果を見る前に凍結**する。

## やるなら守ること

1. 新しい目的関数で較正した結果を、**古い目的関数でも採点して併記**する。
   「目的関数を変えたら成績が上がった」は当たり前なので、それでは何も言えない。
2. 空間保留(5 分割)で一般化を確認する。季節項を足すと過学習しやすい。
3. 変更前後で**地域ゲート 17 件**の内訳を比べる。ゲートは目的関数と独立に
   凍結された地域の物差しなので、ここが改善するなら本物。

## やらない理由(今夜実装しなかった判断)

目的関数は 2026-07-31 に事前凍結した。**成績が下がった直後に目的関数を
変えるのは、動機として最悪**である(「下がったから測り方を変えた」)。
先に数値の修正を確定させ、その上で「季節を測っていない」という
構造上の理由だけで提案し、判断を仰ぐ。
