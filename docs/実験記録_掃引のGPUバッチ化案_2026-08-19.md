# 実験記録: 掃引の並列度はさらに上げても頭打ち — 次の一手は「水準をスレッド添字にするバッチ化」

日付: 2026-08-19
前段: [実験記録_掃引の並列化_2026-08-15](実験記録_掃引の並列化_2026-08-15.md)

**注記**: これは別セッション(GPU寿命を調べる調査サブタスク)からの申し送りで、
較正・目的関数には一切触れていない。インフラ(掃引の速度)だけの話。
利用者裁定により、v28 較正の進行中は着手しない(下記「優先度」参照)。

## きっかけ

GPU の寿命への影響を調べる過程で、較正掃引の実測が「使用率(nvidia-smi)
100% なのに消費電力は 70W 前後(TGP 320W の 23%)」という非対称を示した。
気になったので深掘りした。

## 測定: 並列度を 4→8 に上げても頭打ち(合計スループットはむしろ悪化)

```
単独実行(前段の記録)                146〜149 秒/水準
並列4(前段の記録)                   365〜382 秒/水準 → 1.55 倍速
                                     (他ジョブと GPU 競合下の下限値、と前段が明記)
並列8(今回。conveyorStrength 掃引3本と同時実行のため汚染あり)
                                     879〜952 秒/水準 → 全体 960 秒
                                     (直列換算 1184 秒に対し 1.23 倍速)
```

GPU の電力・温度は並列 4 本時とほぼ変わらず(72〜76W・44〜46℃)、並列度を
上げても動かなかった。**「並列度を上げれば速くなる」は成り立たない。**
前段(2026-08-15)の結論「CPU が空いていても律速は GPU、桁で効かせたいなら
GPU 側(多重格子)を削るしかない」(§「判定2」、さらに遡って 2026-08-06 以来)
を再確認しただけである。

## 診断: なぜ電力が動かないのに使用率 100% か

`src/sim/gpu/ebm_gpu.ts` を読んだ:

- 1 タイムステップにつき `device.queue.submit()` は 1 回だけ(L762)。反復
  (赤黒スイープ、1 ステップ内で最大 512 回)は同一コマンドエンコーダ内に
  CPU 同期なしで連続発行される。GPU→CPU 読み戻しは既定では最終ステップ後
  のみ。→ **反復ごとの同期待ちは無い**(最初にこれを疑ったが外れた)。
- 実在地球 1° 格子は 360×180=64,800 セル。ワークグループ 256 で 254 WG
  (L500)。RTX 4080(76 SM)に対して 1 ディスパッチの規模が小さすぎ、
  カーネル起動オーバーヘッド(約 26µs/dispatch、L660 注記の実測「512反復
  で1 submit 約40ms」から逆算)が実演算より支配的になっている。
- 反復ごとに 1 ワークグループだけの極小カーネル(`polar`, L750)が最大
  512 回/ステップ挟まる。

→ 格子が GPU に対して小さすぎる**コマンド律速**。プロセスを増やす並列化は、
同じ直列の GPU コマンドキューを頭数で割っているだけで足し算にならない。

## 処方箋案(未実装): 水準をスレッド添字の第3軸にする

複数水準を**空間連結せず**、セル (x,y)・水準 L のデータを
`L×cellCount + cellIndex` に配置する。近傍参照(東西南北)は同じ水準の
オフセット内だけで完結するので、空間境界の混線は構造的に起こり得ない。
ディスパッチ回数は水準数に関係なく 1 反復 1 回のまま、ワークグループ数
だけ 254 → 254×N に増える(N=水準数)。

Fable(裏取り用の独立エージェント)に2回、コードを自分で読ませて検証させた:

- **境界混線**: 構造的に回避できる(確認済み)。
- **速度**: N=8 で現実的には**5〜8倍**。ただし `sweepCell` は帯域律速
  (セルあたり約14読み)のため、**「大きく超える」は保証できない**。
  実装前に N=2,4,8 の**ミニベンチマークで 1 ディスパッチの実仕事時間 t1 を
  実測**してから判断すべき、との指摘。
- **障壁**: ①パラメータ(現状は単一 uniform)の水準別配列化、
  ②`measureResidual`/`accumulate` の水準別集計(中程度の手間)、
  ③**較正定数が EBM 単体(`k.*`)でなく step1〜4(風・雲・蒸発)にも効く
  場合、`fields` 全体を水準別にストライド化する必要があり、想定より
  改修範囲が広がる**(一番の見落とし候補として指摘された)、
  ④ VRAM(1 水準約 30MB、N=8 で約 240MB は可、N>32 は要注意)。

前回案(格子を空間連結する/バッファを分けて同じエンコーダに交互発行する)
より構造的に優れる、というのが Fable 2 回分の一致した評価。

## 優先度についての申し送り

これは較正の**速度**を上げるだけで、精度の頭打ちとは無関係(そちらは
目的関数 v6 + v28 較正として既に別トラックで進行中、
[引き継ぎ_2026-08-19](引き継ぎ_2026-08-19.md) 参照)。v28(12h 枠)実行中に
着手する理由はない。やるなら、v28/v29 が一段落してから、まず安い
ミニベンチマーク(数十分)だけ先にやり、5〜8 倍の見込みが実測でも
立つか確認してから大改修に入るかどうかを決めるのが安全。
