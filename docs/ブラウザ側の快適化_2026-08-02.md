# ブラウザ側の快適化(2026-08-02 → 08-03)

利用者の依頼は 6 件:

1. ブラウザ Worker から WebGPU を使えるようにする
2. 操作中は軽量プレビュー、確定後に完全収束計算
3. 変更されたパラメータ以降の段だけ再計算する
4. 実行中計算をキャンセル可能にする
5. 計算過程をリアルタイムで表示する
6. 計算の全体に対する進捗を表示する

**2 は実物を触った利用者の判断で撤回された**(08-03)。プレビューを別に持たず、
本計算の途中経過をそのまま本表示に出す形になった。詳細は下の設計判断。

## 着手前に分かっていた事実

- ブラウザの Worker は**加速器を渡していなかった**(`runPipelineTimed(params)` を
  引数なしで呼んでいた)。つまりブラウザは全部 CPU 実装で走っていた。
- GPU が使えなかった原因は 1 点だけ: `src/sim/gpu/device.ts` が Node 専用の
  `webgpu` パッケージを静的 import していたこと。カーネル 3 本
  (ebm / moisture_trace / soil_water)は `GPU_WORKGROUP_SIZE` /
  `ReadbackStage` / `asBufferSource` しか使っておらず、**シェーダは移植不要**。
- `ebm_gpu.ts` の積分ループは `years×240` 回の submit を **await 一つ無しの
  同期ループ**で回し、読み戻しは最後の 1 回だけ。つまり
  **中断点も進捗の取り出し口も物理的に存在しなかった**。
  4・5・6 はすべてこのループを刻む同じ工事から出てくる。

## 費用の内訳(実測、`scripts/prof_stage_cost.ts`、地球 1°、GPU)

| 段 | 割合 |
|---|---:|
| step5_temperature(EBM) | **97.86%** |
| step6_precipitation | 2.00% |
| 残り 7 段の合計 | 0.14% |

**この偏りが設計のすべてを決めている。**

## 設計判断

### プレビューは廃止した(2026-08-03)

**当初の設計**: プレビューを「途中で止めた確定計算」(格子も物理も同じで
収束予算だけ小さい)とし、確定は明示ボタンで回す。

**実物を触った利用者の判断で撤回した**。曰く「最初から本計算でもあまり
違和感がない、プレビューは要らない」。実際そのとおりで、
軽量プレビューを別に持つ意味は薄かった:

- プレビュー(EBM 4 年/反復 64)でも大陸規模の模様は確定版とよく似ていた。
- 一方で「プレビューか確定か」という状態が UI に増え、バッジと注記で
  常に説明が要る。**説明が要る抽象は、たいてい要らない抽象**である。

置き換えた設計は「**本計算の途中経過をそのまま本表示に出す**」。
別の品質を持たず、走っている 1 つの計算が育っていくのを見せる。
「未確定である」ことは進捗帯が出ていること自体が示し、
帯が消えたときが確定値になる。

収束予算の仕組み(`ConvergenceBudget`)は残してある —
UI からは使わないが、数値の実験(`scripts/exp_*.ts`)が予算を振って測る。

### 実行はボタンでしか始まらない(2026-08-03)

プレビューを廃止した結果、1 回の実行が常に数分になる。触るたびに GPU が
回るのは割に合わないので、**パラメータを変えても計算は始まらない**ことにした
(利用者の判断)。

そのかわり「地図とパラメータがずれている」状態が普通に起きる。
自動実行しない以上これを黙っていると古い地図を最新と誤読するので、
`computedParams`(その地図を計算したときの入力)を控えて UI に必ず出す。

### キャンセルは terminate ではなくメッセージ

Worker を terminate すると WebGPU デバイスと加速器の常駐バッファが
道連れになり、再取得に数百 ms かかるうえ段キャッシュも消える。
協調的な中断にした。そのために計算ループが**イベントループへ制御を返す**
必要がある(Worker の `onmessage` は JS が走っている間は発火しない)。

刻みは EBM の**1 か月ぶんの時間ステップ**ごと(既定 240/12 = 20、約 1 秒間隔)。
この刻み幅は偶然ではなく、途中の気温場を組むために必要な間隔でもある
(下の「進捗と途中結果」を参照)。`setTimeout(0)` ではなく
`MessageChannel` を使う — ブラウザは入れ子の `setTimeout` を 5 段目から
4ms にクランプするため。

### 進捗と途中結果は「書込のみの受け皿」

降水診断 `PrecipDiagBox` と同じ扱いにし、
**渡しても渡さなくても物理結果はビット一致する**ことをテストで担保した
(`tests/unit/sim/run_control.test.ts`)。

途中結果は**本表示に直接出す**(2026-08-03 の変更)。当初は別枠のサムネイルに
出していたが、同じものを二か所に出すより本表示が育つほうが分かりやすい、
という利用者の判断。取り違えの防止は「別の場所に置く」ではなく
「**進捗帯が出ているあいだは確定値ではない**」という一本の規則で行う。

何がいつ届くか:

| 層 | 届くタイミング | 全体に占める費用 |
|---|---|---:|
| 地形 | context 完了(~60ms) | 0.1% |
| ITCZ・風帯・海流・気流 | 各段の完了(合計 1 秒未満) | 0.1% |
| 気温 | **EBM のモデル内 1 年ごと** | 97.9% |
| 降水 | **結合反復ごと**(最大 8 回) | 2.0% |
| 気候区分 | 気温と降水が揃った時点から、降水の更新ごとに組み直す | — |

気温だけ作りが特殊なので注記する。積分の途中に得られるのは
「その瞬間のモデル時刻の粗格子温度」であって月平均ではない。そこで
**1 か月ぶんの時間ステップごとに 1 枚**受け取り、12 枚揃った時点で
1 年ぶんの季節サイクルとみなして表示格子へ落とす。確定結果は末尾 1 年を
毎ステップ積算した本物の月平均なので、**両者は一致しない**。
穴のある季節サイクルを出さないよう、12 か月揃うまでは何も出さない。

気候区分の暫定合成はワーカー層(`src/worker/worker.ts`)に置いた。
これは表示のための合成であって物理の一部ではないので、
パイプラインに入れると「本来まだ存在しない段の出力」が計算層の途中に現れる。

進捗は**単調ではない**。収束しなければ予算を倍にして回し直すので見積もりが
伸びる。そのときは `budgetExtended` を立てて UI に「予算を増やして計算し直して
います」と出す(嘘の進捗バーを作らない)。

### 未計算の層の見せ方(2026-08-03 の手直し)

途中結果を本表示に出す以上、「選んでいる層がまだ無い」状態が必ず生まれる。
最初は地形へ退避して小さなピルで断るだけにしたが、**利用者から
「切り替えができない」と報告された**。原因は退避そのものではなく、
退避したことの示し方が弱かったこと:

- 気候区分・降水・地形のタブが全部同じ絵になる
- 地形は月を持たないので月ボタンも効かなく見える
- **既定のタブ(気候区分)が、EBM のあいだずっと未計算の層**だった

実測で「重い」ではないことを先に確定させた(メインスレッドの最大停止は
6.6 分を通して 39〜102ms、クリックは効いていた)。決め手はキャンバスの指紋が
6 分間まったく同一だったこと。

対処は 3 点セット:

1. **押す前に分かる** — 未計算のタブを淡色化 + ○ 印 + 待ち理由のツールチップ
2. **見れば分かる** — 地図中央に大きな断り書き(小さなピルでは気づけない)
3. **代わりが分かる** — 「いま見られるのは 地形・海流・気圧・風帯」を併記

いずれも e2e で固定した(`interactive.spec.ts`)。

## 段キャッシュの効き目 — 正直な結論

依存関係を実測で洗い出した(各段の `params.*` を列挙):

| 段 | 読むパラメータ |
|---|---|
| context | gridResolutionDeg / terrain / orbital / body |
| step1 ITCZ | body.axialTiltDeg |
| step2 風帯 | body(自転周期・向き・傾斜・半径) |
| step3 海流 | body |
| step4 気流 | body |
| step5 気温 | **atmosphere 全部** + 上流 1〜4 段すべて |
| step6 降水 | atmosphere.surfacePressureBar + **step5 の出力** |
| step7 区分 | 上流のみ |

つまり**気温(97.9%)と降水(2.0%)は上流すべてに依存する**。
利用者パラメータをどれか 1 つ動かした場合、段キャッシュが省けるのは
**全体の 0.2% 未満**である。

実装はした(教訓 §3 の PipelineCache + getOrCompute)し、正しく動く。
効くのは次の 2 つの場合だけ:

- 依存が何も変わっていない再実行を丸ごと省く(教訓 §4 の F5)
- 中断してから同じパラメータで回し直したとき、上流 1〜4 段を使い回す(= 0.2%)

**気温の再計算そのものを省くにはウォームスタートが要る**が、これは
決定性規約に触れるため利用者の判断で保留。前提の検査を用意して回したが、
**検査は不成立に終わった**(次節)。

## 実測(2026-08-02、RTX Lovelace、**他の較正ジョブと GPU 競合あり**)

| | 値 |
|---|---:|
| ブラウザ Worker の旧プレビュー(1°、参考) | 26〜49 秒 |
| 同・加速器 | `WebGPU (nvidia / lovelace)` |
| 本計算の全段(1°、Node/GPU) | 583 秒(内 EBM 570 秒) |
| CPU 実装の本計算(1°) | 1 時間超で未完了(打ち切り) |

数値は競合下のものなので、単独実行なら
`docs/計算費用の課題_2026-08-02.md` の 245 秒に近づくはず。
**比率(EBM が 97.9%)のほうが設計にとって重要**で、こちらは競合に鈍い。

### ヘッドレスで GPU を掴むための設定

Playwright の既定は `chromium-headless-shell` で **GPU が無い**。
そのままだと「No available adapters.」で静かに CPU 実装へ落ち、
「遅いが通る」テストになって GPU 経路の退行を検出できない。
`channel: 'chromium'` + `--enable-unsafe-webgpu` で解決した(playwright.config.ts)。

## ウォームスタートの検査は**不成立**(2026-08-02)

「収束解は開始点に依るか」を、**加速期の年数**(熱容量 1/16 で回す期間)を
2 / 6 / 10 年と変えて開始点を作り分けることで測ろうとした。
結果は 3 惑星 × 3 開始点の 9 ケースすべてで差が**厳密に 0.000°C**。

これは合格ではない。**開始点が一つも変わっていなかった**。
加速期の時定数は τ' ≈ 0.2 年なので 2 年(= 10τ')で既に自分の周期解へ
落ち着いており、6 年でも 10 年でもそこに留まるだけ。全熱容量の相へ入るときの
状態が同一なので、出力もビット一致する。

**教訓 §9 に先に記録されている落とし穴**(「増やしても変わらない」を言う前に、
増えているのが何かを確かめる)を、記録があるのに同じ形で踏んだ。
前回は積分年数、今回は加速期年数 — **どちらも「加速期が伸びるだけ」**だった。
ビット一致は「頑健」ではなく「**独立変数が動いていない**」の徴候として読むこと。

スクリプトには、全ケースがビット一致したら合格にせず「検査不成立」と
言わせる番人を入れた(同じ誤読を二度させない)。

**ウォームスタートの可否は未判定のまま。** 正しく測るには
`computeTemperature` に `initialT` を差し込む口が要る(内部の
`integrate`/`integrateAny` は既に受け取れるが、外へは出ていない)。
その口を開けるのは「検査だけ」の範囲を超えるので、判断を仰ぐ。

## 発見した既存の欠陥(未修正)

`ebm_gpu.ts` の `MAX_STEPS = 8192` は、240 刻みだと**合計 34 年**が上限。
一方 step05 の適応ロジックは周期定常に達しないと全熱容量の年数を
24 → 48 → …(上限 `EBM_MAX_FULL_CAPACITY_YEARS = 64`)と倍増させる。

**48 年 + 加速期 2 年 = 50 年 = 12,000 ステップで上限を超え、
「時間ステップ数が上限を超えた」で落ちる。**
つまり文書化された上限 64 年には**原理的に到達できず**、24 年で周期定常に
達しない惑星は、収束せずと診断されるのではなく**例外で死ぬ**。

`EBM_MAX_FULL_CAPACITY_YEARS = 64` を掲げている以上これは実装の不整合で、
惑星デザイナとしては「地球では起きないが他の惑星では起きる」種類の欠陥。
EBM の数値に触れる変更なので、こちらの判断では直していない。

## 残っている課題

本計算 1 回は数分かかる。途中経過が見えるようになったので待ち時間の体感は
だいぶ変わったが、**総時間そのものは縮んでいない**。費用の 97.9% が EBM
である以上、ここを縮めない限り本質は変わらない。選択肢は 2 つで、
いずれも別の判断が要る:

1. **ウォームスタート**(前提の検査がまだ不成立 — 上記)
2. **多重格子**(`docs/計算費用の課題_2026-08-02.md` の 2 番。独立した大仕事)

また、途中経過のうち**気温だけは費用の 97.9% を占める段の中で 1 年ごとにしか
更新されない**。モデル内 1 年 = 240 ステップなので、確定品質(反復 512)だと
1 更新あたり約 10 秒。ここをもっと細かくしたい場合は、
月の途中でも前年の月平均を差し替える等の工夫が要る(未着手)。
