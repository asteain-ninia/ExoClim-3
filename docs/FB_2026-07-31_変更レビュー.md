## 2. P0 — 次作業前に必ず直す

### P0-1. 棄却実験で標準検証成果物を汚さない

#### 問題

P2-2 の EBM 界面対称化は退行ゲートで棄却され、コードは復旧された。
しかし、その実験中に生成した `out/validate/report.json` と画像が
標準出力として残っている。

この状態では、利用者が棄却モデルの地図を採用モデルの出力と誤認する。
また、完了報告の「退行ゲート PASS」と成果物の
`regressionPass=false` が矛盾する。

#### 修正方針

- 標準採用モデルの出力先は `out/validate/` とする。
- 単独実験は、次のような別ディレクトリへ出す。
  - `out/experiments/p2-2-symmetric-interface/`
  - または実験名・日時を持つ同等のディレクトリ
- 棄却後にコードを戻した場合、標準 `validate` を再実行して
  `out/validate/` を採用 HEAD と一致させる。
- レポートへ次を追加する。
  - Git コミット識別子
  - 実験名または `baseline`
  - 使用した定数のダイジェスト
- コミット識別子を取得できない環境では `unknown` とし、
  架空の値を入れない。

#### 受入条件

- 現在 HEAD で `regressionPass=true`、地域ゲート14/17を再現。
- `out/validate/report.json` のコミット識別子が現在 HEAD と一致。
- 棄却実験を実行しても標準成果物が変わらない。
- 実験成果物から、採用/棄却と実行条件を判別できる。

### P0-2. 合否判定を非有限値に対して閉じる

#### 問題

`scripts/validate_criteria.ts` の判定は大小比較だけである。
JavaScript では NaN との大小比較がすべて false になるため、
全指標を NaN にしても次が PASS する。

```text
evaluateRegression(...) => { pass: true, failures: [] }
evaluateAcceptance(...) => { pass: true, failures: [] }
```

破損した採点、分母 0、空の保留区画などが、CI で正常扱いになる。

#### 修正方針

- `evaluateRegression` と `evaluateAcceptance` の冒頭で、
  全数値を `Number.isFinite` により検査する。
- 配列の各要素も検査する。
- NaN、Infinity、-Infinity は必ず FAIL。
- `gatesPassed`、`gatesTotal` は有限な非負整数とする。
- `gatesPassed <= gatesTotal` を要求する。
- `gatesTotal=0` は合格率 0 とせず、判定不能として FAIL。
- 空の `majorAreaGapPt`、空の `zonalTempAbsDiffsC` も FAIL。

#### 受入条件

- 全指標 NaN の退行判定が FAIL。
- 全指標 NaN の最終受入判定が FAIL。
- Infinity、空配列、ゲート総数0、不正なゲート件数がそれぞれ FAIL。
- 現行正常値は従来どおり PASS。
- 失敗理由に対象指標名と非有限/不正値であることを含める。

`ACCEPTANCE_CRITERIA.regionGatePassRateMin` は 0.7 である。

`docs/要件.md` の 70% は途中目標であり、最終採用基準とは分ける。

次の 3 段階を明示する。

1. **退行防止**
   - 現在 PASS しているゲートを失わない。
2. **途中目標**
   - 地域ゲート70%以上。
3. **最終受入**
   - 地域ゲート17/17。

途中目標と最終受入を同じ `acceptancePass` に混ぜない。

#### 受入条件

- 14/17 は途中目標 PASS、最終受入 FAIL。
- 16/17 も最終受入 FAIL。
- 17/17 だけが地域ゲート最終受入 PASS。

- テストで 12/17、14/17、16/17、17/17 の境界を固定。

## 3. P1 — 保留検証を真に独立させる

### P1-1. 現行の区画別成績を「一般化性能」と呼ばない

#### 問題

現在の定数は全球データを使って較正済みである。
その同じモデルを fold ごとに切って測った 61.7～82.1% は、
空間区画別成績であって、未見データへの一般化性能ではない。

完了報告の

> 現行モデルの一般化ギャップが数値化された  
> 全球73.9%は過大評価

という結論は、fold を除外した再較正前には成立しない。

#### 修正方針

- 現行レポートの名称を次のように変更する。
  - `spatialSliceMetrics`
  - 「全球学習済みモデルの区画別診断」
- `holdout`、`generalizationGap`、`unseen` という語は、
  対象 fold を除外して再較正したモデルにだけ使う。
- レポート JSON に次を持たせる。
  - `trainedExcludingFold: number | null`
  - `isUnseenEvaluation: boolean`
- 現行採用モデルでは `null`、`false`。

#### 受入条件

- 現行モデルの区画別表が未見評価と表示されない。
- `--holdout-fold N` で再較正した状態/最良値を評価した場合だけ、
  fold N を未見評価として報告する。
- 訓練、空間区画診断、真の保留検証、全球を混同しない。

---

### P1-2. ITCZ 目的関数から保留区画の観測漏洩を除く

#### 問題

現在は観測 ITCZ 重心を全球の熱帯降水から作り、その後で
重心座標に対して `keep` を適用している。

したがって、訓練側に残る ITCZ 重心値の計算へ、
保留区画の観測降水が既に混入している。

#### 修正候補

次のいずれかを事前登録し、採用理由を記録する。

1. 保留較正では ITCZ 項を目的関数から外す。
2. 月×経度列の ITCZ 観測値を独立した観測単位とし、
   空間セルとは別の決定的 fold へ割り当てる。
3. 訓練セルだけから重心を再計算する。ただし、欠測・片側だけの重心による
   意味の変化を診断する。

最も単純で漏洩が少ないのは 1。
ITCZ 項を残す場合は、観測重心の生成過程まで分離すること。

#### 受入条件

- 保留区画の観測降水を変更しても、訓練側 ITCZ 目的関数が変化しない。
- または、ITCZ 項が保留較正の目的関数から明示的に除外される。
- テストは最終重心値だけでなく、元観測セルを変更して漏洩を検査する。

---

### P1-3. 地域ゲートの保留漏洩と不均衡を直す

#### 問題

地域ゲートは全球セルで先に採点し、その後、地域枠中心の属す fold 番号だけで
ゲート全体を除外している。

地域枠は複数の30°ブロックへ跨るため、訓練ゲートの判定へ保留セルが混入する。

また、現在の地域ゲート割当数は次のとおりである。

```text
fold 0: 6件
fold 1: 4件
fold 2: 2件
fold 3: 1件
fold 4: 4件
```

目的関数は合格ゲートの絶対件数を加算するため、fold ごとに最大値と
ゲート項の重みが異なる。fold 間の適合度を直接比較できない。

#### 修正方針

- 地域ゲートをセル空間 fold とは別の「地域観測単位」として登録する。
- 各地域ゲートは一つの fold に完全所属させる。
- 訓練時は保留所属の地域ゲートを丸ごと除外する。
- 訓練所属のゲートは、その地域全体を使うことを明示する。
- 完全な空間独立を求める場合は、ゲート領域とセル保留領域が重ならないよう
  分割設計を見直す。
- 目的関数は合格数ではなく、
  `合格数 / 訓練対象ゲート数` などの正規化値を検討する。
- fold 間で地域観測数と主要気候群を可能な範囲で均衡させる。

#### 受入条件

- 保留所属ゲートの観測・モデル値を変更しても訓練目的関数が変化しない。
- 各 fold の訓練対象ゲート数と保留ゲート数を報告。
- fold ごとのゲート項の理論最大値が比較可能。
- `validate` は訓練ゲートと保留ゲートの成績を別々に報告。

## 4. P1 — 適用範囲診断を本当に事前実行する

### 問題

`diagnoseInputs` は「計算前」と説明されているが、
`runPipeline` は全 Step とケッペン判定を完了した後に
`buildDiagnostics` を呼ぶ。

不正入力が配列確保、反復回数、除算などを壊す場合、
診断へ到達する前に例外、過大計算、メモリ不足が起きる。

また、入力診断には次が含まれていない。

- `gridResolutionDeg`
- `perihelionSeasonDeg`
- `rotationDirection`
- 手続き地形の乱数種子
- `landFraction`
- `reliefScale`
- 地形種別

コメント上の「UI スライダー定義域」と、実際の UI 範囲も一致していない。

### 修正方針

- パイプライン冒頭で `diagnoseInputs` を実行する。
- 計算不能な入力と、計算可能だが科学的適用範囲外の入力を分ける。
  - `invalid_input`: 計算せず明示エラー
  - `out_of_domain`: 生の場は計算可能だが科学判定は無効
- 格子解像度など、配列確保やループへ影響する値は必ず事前検査する。
- UI 操作範囲と科学的適用範囲を別定義にする。
- 同じ値を UI と診断へ二重定義しない。

### 受入条件

- `gridResolutionDeg=0`、NaN、Infinity で巨大配列確保や深い計算へ進まない。
- 不正な自転方向、離心率、地形パラメータを事前検出。
- UI 範囲内だが高加熱の組合せは、事後診断で `out_of_domain`。
- 地球条件は従来どおり `ok`。
- UI とヘッドレス実行が同じ診断コードを表示する。

## 5. P2 — テストと実装表現の精度を上げる

### P2-1. `runPipeline` から時計読取りを完全分離する

#### 問題

`runPipeline` は `runPipelineTimed(params).result` を返すため、
戻り値から計測を外しただけで、純粋関数自身は依然として
`performance.now()` を読む。

#### 修正方針

例えば次の構造にする。

```text
runPipelineCore(params, optionalTimingSink)
runPipeline(params)       -> timing sink なし
runPipelineTimed(params)  -> timing sink あり
```

時計を読むのは計測側だけにする。

#### 受入条件

- `runPipeline` の呼出経路に `performance.now()` がない。
- 時計 API を持たない試験環境でも物理計算が動く。
- `runPipeline` と `runPipelineTimed(...).result` の全物理場が一致。

---

### P2-2. 決定性・有限性テストで全出力を検査する

#### 問題

現在の決定性ダイジェストは一部だけを対象とする。
例:

- `monthlyWindV` は有限性だけで、決定性ダイジェストにはない。
- 気圧偏差場がない。
- 海流分類、湧昇、サンゴ礁、流線がない。
- 最暖月、最寒月、氷マスクがない。
- 文脈の地形、日射、海岸距離がない。

「物理結果が配列まで決定的」というテスト名と実際の検査範囲が一致しない。

また、ハッシュ混合の値ごとに `ArrayBuffer` と `DataView` を新規生成しており、
不必要に割当が多い。

#### 修正方針

- `PipelineResult` の全数値配列を列挙する共有検査関数を作る。
- 決定性と有限性が同じ列挙を使う。
- 流線は種類、長さ、全座標を検査する。
- 診断も比較する。
- 8バイトのバッファは一つだけ再利用する。
- または型付き配列を直接比較する。

#### 受入条件

- 任意の一配列だけを改変すると決定性テストが失敗する。
- 任意の一配列へ NaN を入れると有限性テストが失敗する。
- 検査対象一覧が `PipelineResult` の型変更時に更新漏れを検出できる。
- テスト時間とメモリ使用量を修正前後で報告。

### P2-3. 「角半径」を球面距離として実装する

#### 問題

現在の探索は `±R` 行・`±R` 列の正方窓である。
これは球面上の一定角半径ではない。

- 高緯度では同じ経度差の物理距離が短い。
- 正方窓の対角は指定半径を超える。
- 3°半径を2°格子へ丸めると、±4°まで探索する。

現状は「固定セル数」問題を改善したが、
「一定距離または一定角距離」の完了条件には届いていない。

#### 修正方針

- 候補窓を広めに列挙し、各候補を大円距離または近似角距離で絞る。
- 近似する場合は `cos(緯度)` を経度差へ適用する。
- 距離の境界を含む/含まない規則を固定する。
- 惑星半径へ追従させる物理過程なら km 基準を使う。
- 海流表示の重複防止パディングと、
  降水物理の暖海・寒流探索は別要件として扱う。

#### 受入条件

- 赤道と60°緯度で同じ角距離判定。
- 対角方向でも半径内外が正しい。
- 2°格子の3°半径が4°地点を拾わない。
- 0.5°/1°/2°で境界判定が一致。
- 地球1°結果への影響を報告し、必要なら再較正候補として分離。

### P2-4. 状態保存の耐久性表現を正確にする

#### 問題

`saveStateAtomic` は一時ファイルへ `writeFileSync` し、
`renameSync` で置換する。プロセス中断に対する原子的置換としては改善しているが、
一時ファイルの `fsync` を行っていない。

「原子的保存」は概ね正しいが、電源断後も永続化済みとは保証できない。

#### 修正方針

次のどちらかを選ぶ。

1. 一時ファイルを開き、書込み、`fsync`、close、rename を行う。
   必要な環境では親ディレクトリも同期する。
2. 文書を「プロセス中断に対する原子的置換」に限定し、
   電源断耐久を主張しない。

#### 受入条件

- 実装と文書の保証範囲が一致する。
- 既存本体と不完全な一時ファイルがある場合、本体を正常読込できる。
- 置換失敗時に本体を失わない。
- 一時ファイルが残った場合の起動時処理を定義する。
