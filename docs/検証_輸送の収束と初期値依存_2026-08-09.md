# 検証: 水蒸気輸送の収束と初期値依存

日付: 2026-08-09
道具: `scripts/check_transport_warmstart.ts`(GPU 不使用。`dump_transport_inputs.ts` の場を読む)

## 何を調べようとしたか

保存型では同じ月を結合反復で何度も解き直すので、前回の解から始めれば
(温間開始)反復数が減る。だが**速度のために答えが動いてはいけない**。
定常解は初期値に依らないはずだが、収束判定は有限の許容差で打ち切るので、
初期値が違えば許容差ぶん違う解で止まりうる。それが採点に効く大きさかを測る。

## 第 1 版は判定不能だった — そしてもっと重い問題を暴いた

cold(局所平衡から)と warm(前月の解から)を上限 20000 で走らせた:

```
月   cold反復  warm反復   最大相対差
 0     20000     20000      0.00e+0
 3     20000      3878      2.92e-1
 7     20000      1446      2.77e-1
11     20000      7843      3.28e-1

合計  cold 240000 反復 / 297 秒    warm 103422 反復 / 133 秒
```

**cold が全月で上限に張り付いている**(= 収束していない)。したがって
相対差 0.29 は「温間開始が答えを変えた」ではなく「cold が収束していない」
の意味しか持たない。**比較対象そのものが壊れていた。**

## 暴かれた問題: 反復上限は「地球で足りる値」でしかない

段 1 の本番(海面蒸発を源泉とする実配置)では、上限 20000 で
**未収束 0 件**だった。同じソルバが、入力を変えると 20000 でも収束しない。

これは架空の惑星にとって深刻である。本ツールの本題は地球ではない。
**「地球で足りる上限」を固定値で埋め込むと、他の惑星では上限が答えを決める。**
EBM で 3 回踏んだ隠しパラメータと同じ型が、水蒸気輸送でも成立する。

### 収束が遅くなる条件は物理から予測できる

凝結率 λ が小さいほど水は凝結せずに何周も回るので、緩和すべき固有モードが
遅くなる。反復回数はおよそ 1/λ で伸びるはずである。
実装の下限 `Math.max(0.05, ...)`(= 凝結寿命 20 か月)が最悪ケースを決めている。

弱い凝結の惑星(薄い大気・低温・弱い上昇流)ではここに当たる。

### 打った手

上限に達した解を**黙って採点しない**ようにした。二重に塞ぐ:

1. `PrecipitationResult.transport` に未収束数・最悪残差・使った上限を載せる
2. `diagnostics` が未収束を `severity: 'error'` にする
   → `status: 'out_of_domain'` となり、**ケッペン分類を有効な科学出力として
   出さない**(UI・ヘッドレス検証の両方に効く既存の仕組みに乗せた)
3. `validate` の数値的健全性ゲート(非零終了の対象)にも入れた

**「解けていない解を分類して見せる」のは、無いはずの気候を見せることに等しい。**

## 第 2 版(実行中)

比較対象を壊さない形に組み直した:

1. 上限を 400000 まで上げて **cold を収束させる**
2. その解を **1.5 倍に崩したもの**から warm で解き直す
3. 両方が収束したうえで一致すれば「答えは初期値に依らない」

崩した解から始めるのは、前月の解より**厳しい**初期値だからである。
これで一致するなら、結合反復での温間開始は安全に使える。

判定(先に固定):

> 収束した月どうしで相対差が許容差(1e-5)と同程度なら採る。
> 桁で上回るなら温間開始は使わない。**速度のために答えを動かさない。**

## 併せて入れた高速化(答えを変えないもの)

面の法線速度と局所時間刻みは**風と格子だけで決まり、反復では変わらない**のに、
毎反復セルごとに組み直していた(除算 2 回と max 8 回を数千反復ぶん)。
反復の外へ出した。Float64 で保持するので値も丸めも同じ — **ビット一致**。

## 第 2 版の結果 — **収束判定そのものが嘘だった**

```
月   cold反復  収束   warm反復  収束   最大相対差
 0     45025   ○     33119   ○      9.81e-2
 3     46047   ○     32766   ○      1.30e-2
 6     43595   ○     31305   ○      1.41e-2
 9     43505   ○     32135   ○      1.44e-2
```

**両方とも「収束した」と報告しながら、降水が最大 9.8e-2(平均比)違う。**
許容差 1e-5 の 4 桁上である。

原因は判定の定義だった。判定は

```
max|Δw| / 平均W ≤ 1e-5      ← 1 反復あたりの**変化量**
```

で、**方程式の残差ではない**。緩和の遅い系では、解が不動点から遠くても
1 反復の変化はいくらでも小さくなる。**変化量が小さいことは、解けたことを
意味しない。**

### 閉包も証拠にならない

段 1 で「閉包 −0.0%」を判定 1 の合格根拠にしたが、これも弱い。
発散項 ∇·(WV) は隣接セルで打ち消し合うので**全球和は自動的に 0** になり、
局所解が大きくずれていても閉包は合ってしまう。
閉包が見ているのは不均衡の**平均**であって最大ではない。

### したがって、これまでの保存型の数字は無効

段 1(v3 80.413)も段 2(80.440)も、**この嘘の判定で「収束」と報告された解**
の上に乗っている。段 2〜5 の測定は途中で止め、判定を直してから測り直す。

## 直したこと

収束判定を**方程式の残差**にした:

```
residual = max |S − C(W) − ∇·(WV)| / 平均S
```

発散は掃引の中で既に作っている値なので、費用はほぼ増えない。
`MoistureTransportResult.residual` の意味も変わったので型注記を書き換えた。

## 解法を替えた — 極の経度剛性が原因だった

正しい判定で測ると、点ガウス=ザイデルでも 27 万掃引(418 秒)要った。
楕円型に対する点緩和は格子幅の 2 乗で伸びるので当然だが、**桁が大きすぎる**。
較正は数百回パイプラインを回すので、このままでは載らない。

### 診断

```
緯度 89.5° では dx = a·Δλ·cos(lat) ≈ 970 m
  K·Δt / dx² = 3.9e12 / 9.4e5 ≈ 4.1e6      （赤道は 320）
```

極の 1 行は事実上「無限に伝導する」状態で、点緩和では 1 掃引につき
1 セルしか情報が進まない。**行を丸ごと解けばこの剛性は消える。**

### 打った手: 経度方向の線緩和

各行は周期三重対角なので、巡回 Thomas 法(Sherman–Morrison)で直接解ける。
行の行列は風と格子だけで決まり**反復で変わらない**ので、分解は 1 度でよい。

過緩和も測って選んだ(`scripts/bench_transport_relaxation.ts`、地球 1° 月 0):

```
ω     1.0   1.2   1.4   1.6   1.8   1.9
掃引  384   259   171   119   152   発散
```

既定を 1.6 とし、発散を検知したら 1.0 へ落として解き直す自動の仕組みを残す
(拡散の弱い惑星では移流が支配し、過緩和が効かなくなるため)。

### 結果

```
月   cold反復  収束   warm反復  収束   最大相対差   cold(s)
 0       119   ○       127   ○      8.56e-7      0.3
 3       105   ○       100   ○      8.62e-7      0.2
 6       111   ○       111   ○      3.89e-7      0.2
 9       105   ○       100   ○      1.63e-6      0.2
```

**1 回の求解が 0.2 秒**(点ガウス=ザイデルの 418 秒、擬似時間更新の 704 秒)。
段 1 の 1 パイプライン(12 か月 × 7 結合反復 = 84 回)で 21 秒になる。

### 温間開始の判定

**採る。** 収束した解どうしの最大相対差は 1.63e-6 で許容差 1e-5 未満。
答えは初期値に依らない。
