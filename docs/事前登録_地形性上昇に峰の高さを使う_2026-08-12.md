## いまの実装

地形性上昇は**平均標高の勾配**で計算されている(`step06_precipitation.ts`):

```ts
const dhdx = (elev[east] − elev[west]) / (2·dx)    // elev = terrain.elevationMeters（平均）
const upslope = u·dhdx + v·dhdy
liftOro = 1 + orographicBoost · min(2.5, upslope / 800)
```

一方 `earth_crest_1deg.json`(生 ETOPO 60 秒角から作ったセル内 p95)は
**2026-08-02 に作成済みで、`terrain.crestElevationMeters` として読み込まれている**。
使っているのは風上遮蔽(`upwindMountainFactor`)だけで、その遮蔽は
段 3 の保存則移行で `upwindBlockReliefM: 1e9` にして**無効化されている**。

**データ工事は済んでいて、繋がっていなかった。**

## なぜ峰の高さが正しいか

気流は**峰を越える**のであって、セルの平均標高を越えるのではない。
風上側で強制上昇して凝結する量は峰の高さで決まる。
保存型では、そこで降った分だけ W が減って風下が乾く — **雨陰は収支から出る**。
段 3 が遮蔽の乗数を外せたのはこの理屈だが、**風上で絞る力が弱いままだと
収支から雨陰が出てこない**。パタゴニアが 135% 過剰なのはその症状と読める。

## 変えるもの

勾配を作る標高を、平均と峰の**混合**にする。

```
elevLift = elevMean + orographicCrestBlend × (crest − elevMean)
```

- `orographicCrestBlend`(0〜1)。**既定 0 = 従来と 1 ビットも変わらない。**
- 掃く値: 0 / 0.3 / 0.6 / 1.0

**峰の場を気温には使わない。** 気温の高度補正はセルの平均気候を出すもの
なので平均標高が正しい。利用者が懸念した「1 セルだけ持ち上げて量子化が
歪む」問題は、**用途ごとに違う統計を引くこと**で避ける。

| 用途 | 使う標高 | 理由 |
| --- | --- | --- |
| 気温の高度補正 | 平均 | セルの平均気候だから |
| **地形性上昇・雨陰** | **混合(今回)** | 気流は峰で止まる |
| 陸面・海陸判定 | 平均 | 面積の話 |

## 予測(先に書く)

- **パタゴニアの過剰降水が減る**(135% → 100% 方向)。風上のチリ側で
  絞られるぶんが増え、風下が乾く。
- **チベットの北(タリム盆地)も乾く**方向に動く。比は 1.18 と小さいが
  絶対差が +714m あるため。
- 熱帯アンデスの東(アマゾン西縁)は**湿る**(風上側だから)。
  アマゾンは既に観測比 1.34 と過剰なので、**ここが悪化する筋がある**。
- 全球の陸平均降水はやや**増える**(絞りが強くなるので山地で降る)。

**外れる筋**: 混合した勾配は「隣接セルの p95 の差」なので、
**峰の位置がセル境界と噛み合わないと勾配が暴れる**。
その場合は上昇と雨陰が同じ場所で交互に出て、場が汚れる。
掃引で v3 が単調でなく暴れたらこれを疑う。

## 判定(先に固定する)

較正 v20(586 評価)の定数の上で測る。

1. **patagonia の年降水が観測比 1.35 から 1.15 以下へ下がる。**
2. **アマゾンが観測比 1.5 を超えない**(現在 1.34。風上側の過剰の番人)。
3. **v3 が 84.44 から 1.0 以上落ちない。**
4. **大分類が落ちない。**
5. **v3 が混合率に対して単調**(暴れの番人。単調でなければ「外れる筋」を疑う)。

1〜4 を満たすうち v3 が最良の値を採る。全部満たす値が無ければ棄却し、
**そのときは「峰の高さでは足りない」と結論して地形の線を閉じる**。

- パタゴニアだけを見て採否を決めること。全 17 ゲートと大分類・詳細も必ず出す。
