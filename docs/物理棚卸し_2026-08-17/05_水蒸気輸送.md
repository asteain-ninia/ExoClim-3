## 1. 物理現象の全数列挙

### 1.1 保存型の骨格 — 「月ごとの定常な水の収支を閉じる」

**(a) 素人向け説明**

空の上に「水蒸気の池」があると思ってほしい。池の水位が**可降水量 W**(mm)で、
これは「その場の空の水を全部絞って地面に落としたら何 mm 溜まるか」という量である。
実物の地球では平均 25mm ほど(コップ 1 杯にも満たない)。

この池には 3 つの出入りがある。

1. **入ってくる**: 海面から蒸発した水、陸から蒸発散した水(= 源泉 S)
2. **出ていく**: 雨として降る(= 凝結 C)
3. **流れていく**: 風が隣へ運ぶ(移流)、かき混ぜで隣へにじむ(渦拡散)

1 か月という時間で見れば、池の水位はもう釣り合っている(理由は §1.15)。
だから「入る = 出る + 流れ去る」が各セルで同時に成り立つ点を探せばよい。
その連立方程式を解くのがこのモジュールである。

**重要な性質**: 昔のモデルは「風上に海があるか」という**到達可能性**を計算して
降水量に換算していた。だから水は湧いたり消えたりできた。いまは違う。
**どこかのセルで多く降らせれば、その水は必ず下流のどこかから消える。**
これが「保存型」の意味であり、同時に「源泉を間違えると誤差が全球へ配られる」
という危うさの正体でもある。

**(b) 実装式**

`moisture_transport.ts` の冒頭コメント(9〜16 行)が正本:

```
0 = S_i − C_i(W) − (1/A_i) Σ_f Φ_if
S_i = 海面蒸発 + 陸面蒸発散                          [mm/月]
Φ_{i→j} = L_f { u_n⁺ W_i + u_n⁻ W_j − κ (W_j − W_i)/d_f }
C_i = λ_i G_i W_i                                   [mm/月]
```

セルごとの離散形は 275〜276 行のコメントが正確:

```
diag·w_i − cE·w_E − cW·w_W − cN·w_N − cS·w_S = S_i
diag = rate + ex + outRate
```

- `rate`(= λG)は `moisture_transport.ts:281`、`rateArr[i] = max(1e-6, condensationRatePerMonth[i])`
- `ex`(鉛直輸出)は `:282`。**本経路では常に 0**(§1.16)
- `outRate`(流出係数)は `:263-272`
- 隣接係数 `cE/cW/cN/cS` は `:277-280`
- 最終出力 `condensationMm[i] = max(1e-6, rate) × W_i` は `:517`

**(c) 定数** — §2 の表。

### 1.2 離散化 — 風上有限体積・共有面フラックス

**(a) 素人向け説明**

セルの境目(面)を水がどれだけ通るかを数えるとき、**上流側のセルの水位を使う**。
「風は上流の空気を運んでくるのだから、運ばれる水の量は上流の量で決まる」という、
当たり前の理屈である。

これを「両側の平均」でやると、強い勾配のところで**水位がマイナスになる**
(池の水がマイナス mm という無意味な解が出る)。だから風上を使う。

もう 1 つの肝は、**面の流量を 1 回だけ計算して両側で共有する**こと。
セル A から出た水は必ずセル B に入る。別々に計算すると端数が合わず、
水が湧いたり消えたりする。共有面にすることで、
足し合わせがきっちり 0 になる(Σ A_i div = 0)ことが保証される。

**(b) 実装式**

- 面の法線速度: `:248-251`。`unE = 0.5(uM[i] + uM[iE])`(両側平均 = 共有面で一意)
- 面積・辺長の球面計量: `:185-194`。
  - `areaM2[row] = a² Δλ Δφ cos(緯度中心)` (`:187`)
  - `lenNorthM[row] = a Δλ cos(北面の緯度)` (`:191`)、**極の辺長は 0**(`:190` の `max(0, cos)`)
  - `dxCenterM[row] = a Δλ cos(緯度)`(拡散の分母)(`:188`)
- 経度は周期境界(`wrapCol`、`:244-245`)、南北は `iN/iS = -1` で閉じる(`:246-247`)
- 風上の取り方: 流出側 `max(0, unE) + max(0, -unW)`(`:264-266`)、
  流入側 `max(0, -unE)`(`:277`)。**片方だけが必ず 0** になるのが風上差分。
- 風の単位変換 m/s → m/月: `:199-202`、`SECONDS_PER_MONTH = 30.44 × 86400 = 2,630,016 s`(`:29`)

**保証されている不変量**(`tests/unit/sim/moisture_transport.test.ts`):

| 不変量 | 行 | 判定値 |
| --- | --- | --- |
| 全球水収支 Σ A(S−P)/ΣA·S | :22 | ≤ 1e-4 |
| 非負性(W・C とも) | :44 | ≥ 0 |
| 移流の向き(東風で源の西が湿る) | :59 | — |
| 解像度不変(2°/4° の全球平均 W) | :73 | 5% 以内 **← 疑い S-03** |
| 凝結率 0 でも発散しない | :105 | 有限 |
| 無風・一様源で W = S/λ(解析解) | :116 | 4 桁一致 |
| 決定性(同入力同出力) | :128 | ビット一致 |

**(c) 定数**: なし(格子と半径だけで決まる)。ただし **格子解像度が実質の定数として
効いている**(§4)。

### 1.3 凝結項の陰的扱いと下限

**(a) 素人向け説明**

「1 か月に何回ぶん雨として抜けるか」を rate と呼ぶ。地球の陸では
rate ≈ 15.7 回/月、つまり **池の水は 1.9 日で入れ替わる**。

これを「今の水位 × rate だけ引く」と素直に書くと、rate が大きいときに
引きすぎてマイナスになり、計算が振動して壊れる。だから
**「解いた後の水位に rate を掛ける」**形(陰的)にする。方程式の対角に足すだけなので、
rate がどれだけ大きくても絶対に壊れない。

**(b) 実装式**

- 対角へ加算: `diagArr[i] = rateI + exI + outRate`(`:286`)。陽的な減算はどこにも無い。
- **下限 `max(1e-6, ...)`**(`:281`、`:517`): rate が厳密に 0 だと水が無限に溜まるため。
- **もう 1 段上の下限 `max(0.05, ...)`** が呼び出し側にある:
  `step06_precipitation.ts:1214`
  ```ts
  rate[i] = Math.max(0.05, (travelKmPerMonth / Math.max(1, lKm)) * (G[i] ?? 0));
  ```
  → **疑い S-07**(裸の数値、しかも地球配置では一度も発火しない)

**(c) 定数**: `1e-6`(モジュール内、無名)、`0.05`(step06 内、無名)。
どちらも SPACE 外・仕様書に記載あり(spec §7 に `rate = max(0.05, λ·G)` と明記)。

### 1.4 渦拡散(スカラー / 場の切替)

**(a) 素人向け説明**

風の月平均だけでは、実物の「移動性低気圧が海と陸をかき混ぜる」動きが表せない。
台風や温帯低気圧は 1 週間で来て去るので、月平均すると消えてしまう。
その混ぜ効果を「濃いところから薄いところへ、勾配に比例して染み出す」という
拡散の形で代表させている。これが渦拡散 D(m²/s)。

**重要**: 拡散は**水を湧かせない**。ある場所へ染み出した水は必ず別の場所から
減っている。だから保存則を壊さない。もし同じ効果を「源泉に足す」形で書くと、
陸のど真ん中で水が湧いてしまう(2026-08-15 の設計文書がこの誤りを名指ししている)。

**確定事項(2026-08-16〜17)**:
- D は全球一定で、**移流が担うべき輸送を代行している**
  (`docs/実験記録_渦拡散は輸送を代行していた_2026-08-16.md`)。
  下げると分布形は観測へ近づくが(1% 分位 64 → 21、観測 9)、内陸が乾いて成績が落ちる。
- C→B 誤分類セルでは **拡散が唯一の輸入源**(+25.0mm/夏半年)であり、
  移流は輸出側(−25.8)。**拡散は命綱**(`docs/診断_拡散は命綱で移流が犯人_2026-08-17.md`)。
- 拡散係数を定数とする仮定は文献上も正当化しがたい
  (`docs/調査_他のモデルは同じ壁に当たっているか_2026-08-17.md`)。

**(b) 実装式**

- スカラー / 場の両対応: `:152-158`
  ```ts
  const diffSrc = options.diffusivityM2PerS ?? 0;
  const diffIsField = typeof diffSrc !== 'number';
  const diffAt = (idx) => (diffIsField ? diffSrc[idx] : diffSrc) * SECONDS_PER_MONTH;
  ```
- **面の値は両側セルの平均**(共有面で一意 = 保存的): `:258-262`
- 流出側への寄与: `:268-271`。`(lenMeridional(dE+dW))/(area·dxC) + (lenN·dN + lenS·dS)/(area·dyCenter)`
- 流入側: `:277-280` の `dE/dxC` などの項

**場の供給元 = `STORM_DIFFUSION`**(`step06_precipitation.ts:809`、既定 `boost = 0`):

```ts
D(i) = K.moistureEddyDiffusivityM2PerS × (1 + STORM_DIFFUSION.boost × stormMix[i])
```
(`step06_precipitation.ts:1220-1228`)。`stormMix[i] = supplyW × exp(−coastKm/decayKm)`
は `convertToPrecip` の `:2468` で書かれる。

**boost = 0 のとき `stormMix` 配列すら確保されない**(`:1149`)ので、
スカラー経路と厳密にビット一致する。テスト
`tests/unit/sim/diffusion_field.test.ts:43` が「スカラーと全セル同値の場が
厳密に一致」を担保している。

**(c) 定数**

| 定数 | 値 | SPACE | ゲート |
| --- | --- | --- | --- |
| `moistureEddyDiffusivityM2PerS` | 2,977,275.94 | **あり** [5e5, 3e6] | 常時 |
| `STORM_DIFFUSION.boost` | 0(コード内可変) | なし | 0 で場を作らない |
| `stormMoistureDecayKm` | 1964 | **外した**(2026-08-17) | boost>0 のときだけ生きる |

### 1.5 解法 — 行方向の線緩和(周期三重対角 + Sherman–Morrison)

**(a) 素人向け説明**

連立方程式は、一気に解くには大きすぎる(1° 格子で 64,800 元)。
そこで「1 行(同じ緯度の 360 セル)をまとめて厳密に解き、それを南北に繰り返す」
という解き方をしている。

なぜ行をまとめるのか。**極の近くではセルが横に潰れて幅 1km 以下になる**。
緯度 89.5° では東西の幅が約 970m しかなく、拡散の結合の強さが赤道の
1 万倍以上(4.1e6 対 320)になる。この状態で「1 セルずつ順に直す」やり方をすると、
情報が 1 回の掃引で 1 セルしか進まず、事実上永久に終わらない。
**行を丸ごと直接解けば、この硬さは消える。**

経度は輪になって繋がっている(周期境界)ので、普通の三重対角ではなく
「角に 1 つ余分な要素がある」形になる。これは Sherman–Morrison という
古典的な技法で、三重対角を 2 回解くだけで処理できる。

**(b) 実装式**

- 分解 `factorizeRow`: `:315-355`。`gamma = -diag[0]`(`:316`)、
  Thomas 法の前進消去(`:329-338`)、補正ベクトル z の解(`:339-354`)
- **閾値凝結を使わないときは分解を 1 度だけ**作って使い回す: `:358-364`
- 掃引本体: `:407-478`
  - 右辺(南北は既知値、東西は陰的): `:419`
  - Thomas 法の前進・後退: `:453-463`
  - Sherman–Morrison の補正: `:464-469`
  - 更新 + SOR + 非負クリップ: `:470-476`
- **掃引方向の交互化**: `:406` `const rowForward = it % 2 === 1;`
  南北の情報は行から行へ伝わるので、風向と揃った掃引の回に一気に進む。決定的。

**逐次過緩和(SOR)**: `:172` `let relaxation = options.relaxation ?? 1.6;`

実測に基づく既定値(`:166-168` のコメント、`scripts/bench_transport_relaxation.ts`):

| ω | 1.0 | 1.2 | 1.4 | 1.6 | 1.8 | 1.9 |
| --- | --- | --- | --- | --- | --- | --- |
| 掃引数 | 384 | 259 | 171 | **119** | 152 | 発散 |

**発散検知で 1.0 へ落として最初からやり直す**(`:483-498`)。
拡散が弱く移流が支配する配置(他の惑星で起こりうる)では 1.6 が発散するため。
**ω は不動点を変えない**(収束点では w = wGs)ので、較正定数ではなく SPACE にも入れない。

**(c) 定数**: `1.6`(既定)、`1.0`(フォールバック先)。どちらも無名の数値だが、
「答えを変えない量」であることが証明されている(§3 の S-18 で別の懸念を挙げる)。

### 1.6 収束判定と反復制御

**(a) 素人向け説明**

「収束した」の定義を間違えると、**解けていない答えに成績が付く**。
これは 2026-08-09 に実際に起きた。当時は「1 回の掃引でどれだけ動いたか」で
判定していたが、これは緩慢に動く系ではいくらでも小さくなるので嘘をつく。
初期値の違う 2 本がどちらも「収束」と報告しながら、降水が 9.8% 違った
(許容差 1e-5 の 4 桁上)。

いまは**方程式そのものの残差**、つまり「入る − 出る − 流れ去る」の残り物の
最大値を、源泉の平均で割った無次元量で判定している。

**全球の水収支(閉包)は収束の証拠にならない。** 発散項は隣接セルで打ち消し合うので、
局所解が大きくずれていても全球和は自動的に 0 になる。閉包が見ているのは
不均衡の**平均**であって**最大**ではない(`:390-393` のコメント)。
**現行の閉包 −0.0% は「水が漏れていない」ことの証明であって、
「解けている」ことの証明ではない。**

**(b) 実装式**

- 残差の定義: `:438-447`(掃引前の不均衡の絶対値)→ `:479` `residual = maxImbalance / meanSource`
- 基準量: `:369-371` `meanSource = max(1e-9, Σ max(0,S) / N)` ← **面積重み無し(疑い S-19)**
- **NaN を素通りさせない**: `:449` `if (!(absImb <= maxImbalance))`(比較が全て false になる罠)
- 発散判定: `:482` `!Number.isFinite(residual) || residual > 10 * bestResidual`
- 許容差: `:159` 既定 `1e-5`。step06 は上書きしない
- 反復上限: `:160` 既定 4000、**step06 は 20000 を渡す**
  (`step06_precipitation.ts:141` `TRANSPORT_MAX_ITERATIONS = 20000`)。
  既定 4000 では 84 か月分が未収束のまま残った(2026-08-09)。
- **未収束を黙って採用しない**: `step06_precipitation.ts:1260-1265`、
  `CONSERVATIVE_STATS.nonConverged` / `worstResidual` に積み、
  `evaluateNumericalSoundness` の凍結済み関門へ渡る。

**(c) 定数**

| 定数 | 値 | 所在 | SPACE | 性格 |
| --- | --- | --- | --- | --- |
| `tolerance` | 1e-5 | moisture_transport.ts:159 | なし | 数値 |
| `maxIterations`(既定) | 4000 | :160 | なし | 数値 |
| `TRANSPORT_MAX_ITERATIONS` | 20000 | step06:141 | なし | 数値・答えを決めてはならない |

### 1.7 凝結寿命 λ の意味 — **物理として最も疑わしい 1 個**

**(a) 素人向け説明**

λ は「空の池の水が、雨として抜けるまでの速さ」の逆数である。
λ が大きいほど水はすぐ降り、遠くへ運ばれない。

いまの実装は、**非保存時代の「水が消える距離 L」を、そのまま凝結寿命に読み替えた**
ものである。「基準風速 U_ref で 1 か月に進む距離を、距離 L で割る」= λ。

```
λ = U_ref / L
U_ref = 10.95 m/s → 1 か月に 28,805 km 進む
L(陸) = 1,837 km  → λ = 15.68 /月 → 滞留 1.94 日
L(海) = 1,627 km  → λ = 17.70 /月 → 滞留 1.72 日
```

**実物の大気の水の滞留時間は約 9 日である。モデルは 5 分の 1 しかない。**

これは 2026-08-13 に測定済みで(`docs/実験記録_水の滞留時間_2026-08-13.md`)、
**物理として明確な誤りだが、直すと成績が 5 点落ちる**ことが分かっている:

```
基準風速  滞留(陸)  v3      大分類  南極比  サハラ比
10.95     1.9 日   85.199  74.46   0.02   4.74  ← 現行
 2.7      7.7 日   80.322  71.73   0.31   4.15  ← 実物相当
```

較正はこの定数を SPACE に持っており、**全球 RMSE にとって最適な位置として
1.9 日を選んでいる**。つまり**モデルの他の部分の誤りを、速すぎる凝結が補償している**。

**(b) 実装式**

`step06_precipitation.ts:1208-1215`:
```ts
const travelKmPerMonth = (K.condensationRefWindMs * SECONDS_PER_MONTH) / 1000;
for (let i = 0; i < N; i++) {
  const lKm = terrain.landMask[i] ? K.moistureDecayLandKm : K.moistureDecayOceanKm;
  rate[i] = Math.max(0.05, (travelKmPerMonth / Math.max(1, lKm)) * (G[i] ?? 0));
}
```

**λ と G は互いに縮退している**(αG と λ/α は同じ方程式を与える、
`step06_precipitation.ts:71-79` のコメント)。したがって λ を独立に検証する道は
**W の絶対値ただ 1 つ**である。実物 25mm に対し、モデルは診断時点で 3.36mm
(`step06_precipitation.ts:2501` のコメント)。**7 分の 1 である。**

| 定数 | 値 | SPACE | 備考 |

| `condensationRefWindMs` | 10.952465793490411 | **あり** [4, 14] | 上限側でもなく中央付近 |
| `moistureDecayLandKm` | 1837.36 | **あり** [1100, 2400] | **代理場の減衰長も兼務(S-06)** |

### 1.8 源泉 S の構成 — 海面蒸発 + 陸面蒸発散

**(a) 素人向け説明**

池に入る水は 2 種類しかない。

**海から**: 海面の温度で決まる飽和量と、実際の湿り具合(80%)の差に、
風速を掛けたものが蒸発量になる。風が強いほど、海が暖かいほど、空気が乾いているほど蒸発する。
これは「バルク式」といって観測から確立した形で、地理情報を一切使わない。

**陸から**: 土壌バケツ(根群域 600mm)が持っている水のうち、
気温で決まる可能蒸発散のぶんだけ実際に蒸発する。乾いた砂漠からは出ない。

**保存則の下では源泉の誤りが致命的**である。非保存なら局所に留まる誤差が、
保存則の下では下流へ運ばれて非局所になる。だから
**蒸発系の定数は SPACE に入れない**(`scripts/optimize_lib.ts:28-30`):

> 源泉を目的関数で動かせるようにすると、保存則が「源泉の誤りを増幅する装置」から
> 「源泉の誤りを隠す装置」へ変わる。

**(b) 実装式**

源泉の組み立て: `step06_precipitation.ts:1200-1207`
```ts
if (!evapCache.v) evapCache.v = computeOceanEvaporation(ctx, temperature, airflow);
src[i] = terrain.landMask[i] ? (etM?.[i] ?? 0) : (oceanE?.[i] ?? 0);
```
(`etM = soil.actualEtMm[m]`、`oceanE = evapCache.v.monthlyOceanEvapMm[m]`)

海面蒸発(`evaporation.ts:92-139`):
```
E = ρ_a · C_E · |V| · q_s(T_s) · (1 − RH)
q_s(T,p) = ε e_s(T) / (p − (1−ε) e_s(T)),  ε = 0.622   (:46-50)
ρ = ρ_ref · 288.15 / (T + 273.15)                      (:123)
|V| = max(evapMinWindMs, |風|)                          (:122)
T ≤ seaFreezeC のセルは 0(氷面からの昇華は無視)      (:119)
mm/月 = E[kg/m²/s] × SECONDS_PER_MONTH                 (:127)
```

飽和柱水量 `saturatedColumnMm`(`evaporation.ts:72-77`)は CRH と virga の分母:
```
W_sat = q_s(T_s) · p_s / (g · (α+1)),  α = 2.5
```
**α = 2.5 は較正定数ではない**(`:67-68` に明記、SPACE 禁止)。
地球の 288K/1013hPa で W_sat ≈ 31mm、観測の可降水量 25mm と比べて RH 0.8 —
蒸発式で使う海上相対湿度 0.8 と一致する。**独立の 2 つの根拠が合っている**。

### 1.9 凝結率係数 G の構成 — **ここが降水の主因**

**(a) 素人向け説明**

λ が「どのくらいの速さで降るか」の全球の基準だとすれば、
G は「その場所は基準の何倍降りやすいか」を表す倍率である。
山にぶつかって持ち上がるところは降りやすく(G > 1)、
高気圧の下で空気が沈んでいるところは降りにくい(G < 1)。

**2026-08-17 に、C→B 誤分類(失点の 32%)の主因は W ではなく G だと確定した**
(`docs/実験記録_規定風の路線を打ち切る_2026-08-17.md`):

```
G(凝結率)   0.80 / 1.83 = 0.44   ← 2.3 倍の欠損。主因
W(可降水量) 2.79 / 3.19 = 0.87   ←   1.15 倍
P(降水)     63 / 183   = 0.35   ≈ 0.44 × 0.87 ✓
```

そして G の欠損の主因は**沈降抑制**(C→B の残存 0.480 対 健康な C の 0.712)。

### 1.10 virga(雲底下の再蒸発)— 既定 0、外側反復つき

**(a) 素人向け説明**

砂漠では、雲から雨粒が落ちても地面に届く前に蒸発してしまう(virga = 尾流雲)。
乾いた空気ほど、弱い雨ほど多く失われる。

**保存型では「消す」のではなく「そもそも凝結しなかったことにする」**のが正しい。
消してしまうと水の帳尻が合わなくなる。凝結しなかった水は空に残り、
運ばれて別の場所で降る。だから **rate を (1 − 失う割合) 倍して解き直す**。

ところが失う割合は降水量に依存する(弱い雨ほど多く失われる)ので、
解いて→割合を計算して→また解いて、を繰り返す**外側反復**が必要になる。

**(b) 実装式**

`step06_precipitation.ts:1339-1402`。
- 失う割合(Gregory 1995 の形): `:1348`
  ```ts
  lost = min(subCloudEvapMaxFrac, subCloudEvapCoef × (1 − rh) / √p)
  rh = min(1, water[i] / W_sat)          // ← 保存型では W から厳密に取れる (:1346-1347)
  ```
- rate の更新(適応緩和): `:1361-1364` `next = prev + α(target − prev)`
- **収束は「緩和前の差」で測る**: `:1372`
  ```ts
  maxChange = max(maxChange, |target − prev| / max(1e-6, rate[i]))
  ```
  以前は `next − prev = α(target − prev)` で測っており、
  **α が小さいほど「収束した」ことになっていた**(2026-08-15 に発覚、
  段 25 の不変量テストが 3% 超過として捕捉)。
- 適応緩和: `:1394-1396` α = 1 から始め、残差が増えた回だけ半減(下限 0.1)、
  減った回は 1.5 倍(上限 1)。固定 0.6 では 78/204 しか収束せず、
  固定 1.0 では 184/204、**適応で 204/204**。
- 許容差 `VIRGA_TOLERANCE = 5e-3`(`:148`)、上限 `VIRGA_OUTER_ITERATIONS = 60`(`:103`)。
  6 → 60 へ上げた理由: 6 で足りるか一度も確かめられておらず、
  `subCloudEvapCoef = 1` で **216 か月ぶん未収束**になった。
- 未収束は `CONSERVATIVE_STATS.virgaNonConverged` に積む(`:1404`)。

**既定 `subCloudEvapCoef = 0` かつ `crhInner = null` のときは、
外側反復に入る前に return する**(`:1305-1308`)。出荷時の費用はゼロ。

### 1.11 CRH(柱相対湿度)と CRH_INNER — 既定 0

**(a) 素人向け説明**

「どれだけ水蒸気が届いたか」ではなく「その場の空気が持てる量に対してどれだけか」で
雨が決まる。暑い砂漠は持てる量が巨大なので、そこそこ水があっても相対湿度は低く、
雨にならない。観測では熱帯海上の降水が **P ∝ exp(15.6·CRH)** と指数的に応答し、
CRH ≈ 0.75 で点火して 0.5 では 2 桁落ちる(Bretherton et al. 2004)。

**CRH_INNER は「解き方」の話である。** CRH は W から作られ、その W を決める方程式の
係数に CRH が入る。つまり自己参照している。素直に書くと
「前回の W から作った CRH で今回の W を解く」= **1 段遅れの帰還**になり、
2 周期の振動を生む(2026-08-15 に偶奇分裂として実測)。
CRH_INNER を有効にすると、外側反復の中で**いま解いている W** から CRH を作り直す。
**不動点は変わらない**ので、物理の変更ではなく解き方の変更である。

**(b) 実装式**

- 通常(G へ畳み込み): `convertToPrecip:2486-2516`
  ```ts
  crh = crhFromWater && waterMm ? min(1, waterMm[i]/W_sat) : min(1, supply[i]/(crhSupplyNormPerQSat·qSatLocal))
  crhFactor = exp(crhSuppressionSharpness × (crh − 1))
  ```
- CRH_INNER 有効時: `step06_precipitation.ts:1354-1360`(外側反復の中で毎回作り直す)
- 受け皿の生成条件: `:1142-1145`
  ```ts
  CRH_INNER.enabled && K.crhSuppressionSharpness > 0 && K.crhFromWater > 0
  ```
- 診断の締め直し `finishDiag`: `:1294-1302`
  (「診断は実際に走った演算子のものでなければならない」)

**鋭さ 0 では crhFactor が恒等的に 1** なので、CRH_INNER を有効にしても
答えは 1 ビットも動かない。

**(c) 定数**

| 定数 | 値 | SPACE | ゲート |
| --- | --- | --- | --- |
| `crhSuppressionSharpness` | **0** | なし | 0 で機能ごと無効 |
| `crhFromWater` | 1 | なし | 1 = W/W_sat、0 = 代理場 |
| `crhSupplyNormPerQSat` | 2.0 | なし | `crhFromWater = 0` のときだけ生きる |
| `CRH_INNER.enabled` | false | なし | 鋭さ 0 では無意味 |

**履歴**: 4 → 0 へ差し戻し(2026-08-14)。4 では結合反復が収束せず、
`npm test` の 2 件が落ちた。**収束しない値は解ではないので既定にできない。**

### 1.12 結合反復(降水 ⇄ 土壌 ⇄ 陸面供給)

**(a) 素人向け説明**

雨が降ると土が湿り、土が湿ると蒸発散が増え、蒸発散が増えると雨が増える。
鶏と卵なので、繰り返して落ち着き先(不動点)を探す。
これをやらないと、海から遠い赤道内陸が立ち上がれずに砂漠化する。

**(b) 実装式**

`step06_precipitation.ts:1610-1749`。1 回の反復の中身:

2. 陸面供給 `landSource[i] = landRecyclingStrength × min(1, 実蒸発散/PET基準)`(`:1638-1641`)
3. 風上追跡 12 か月ぶん(`:1644` `traceAllMonths`)→ 代理供給場 `supplies2`
4. 月ごとに `monthlyConvert` → 保存型なら `conservativeMonth`(`:1650-1654`)
5. 後処理(冬季床の再配分 + 月平滑、いずれも陸のみ・年総量保存)(`:1655`, `:1449-1526`)
6. 残差 = 陸面積重み平均 |ΔP|(`:1658`、`:1529-1544`)
7. 適応緩和 / Anderson 加速(`:1680-1728`)

**収束判定**: `COUPLING_TOLERANCE_MM_PER_MONTH = 0.2`(`:697`)、
上限 `COUPLING_MAX_ITERATIONS = 24`(`:716`、8 → 24 へ。傾斜 80° の惑星が

### 1.14 月の定常解という近似の妥当性

**(a) 素人向け説明**

「1 か月ぶんを一気に、時間発展させずに解く」というのは乱暴に見えるが、
**大気の水は 1 か月よりずっと早く入れ替わる**ので正当化できる。

実物の大気中の水の滞留時間は約 9 日。1 か月(30.44 日)の 3 分の 1 以下なので、
月の途中で「入る」と「出る」はもう釣り合っている。だから月平均の場に対して
定常解を解くのが妥当である。

**モデルではこの正当化がむしろ過剰に成り立っている。** モデルの滞留時間は
陸 1.94 日・海 1.72 日で、1 か月の **6% 以下**しかない。定常近似としては
極めて安全だが、それは「凝結が実物の 5 倍速い」という物理の誤りの裏返しである(§1.7)。

**(b) 定量的な裏付け**

| 量 | モデル | 実物 | 比 |
| --- | --- | --- | --- |
| 滞留時間(陸) | 1.94 日 | ~9 日 | 1/4.6 |
| 滞留時間(海) | 1.72 日 | ~9 日 | 1/5.2 |
| 全球平均 W | 3.36mm(2026-08-13 の診断) | 25mm | 1/7.4 |
| 定常近似の余裕(滞留 / 1 か月) | 0.064 | 0.30 | — |

**注意**: 月の定常解は「月内の時間発展を捨てる」だけでなく、
**月をまたぐ貯留の持ち越しも捨てている**。滞留 1.9 日ならこれは問題にならないが、
滞留を実物の 9 日へ直したときには「月境界での W の不連続」が新しい誤差源になりうる
(現状は各月が独立に定常解を持つ)。**要測定**。

輸送の初期値の履歴が変わりうる**。
`:1646-1648` のコメントが「収束後に走らせ直すと最終場と厳密には一致しない」と
認めており、この非可換性は既知。

**S-24 [C] 代理場トレースが保存型でも毎結合反復 12 か月ぶん走る。**
`:1644` `traceAllMonths(landSources)`。保存型ではこの出力の役割は
**ゲートの引数と再循環の代理**だけになったが、費用は段 6 以前と同じ。
GPU 加速はある(`:1018` `opts?.accel?.moistureTrace`)が、
CPU 経路では 1 セルあたり最大 200 ステップの追跡。
費用の内訳は EBM が 97.9% を占めるという 2026-08-10 の測定があるので
支配的ではないが、**保存型になっても手を入れていない**という事実は記録に値する。

**S-25 [C] `CONVERGENCE_SMOOTH` の固定角が収束の空間スケールを決めている。**
`:389` `DIVERGENCE_SMOOTH_DEG = 1.5`。2026-08-15 に、収束指数の空間相関長が
100〜170km しかなく、40° 付近で 1.5° ≈ 130km と**測った相関長と一致する**ことが
判明している。実物の温帯低気圧の収束帯は 1000km 級で 1 桁足りない。
**固定角なので緯度で実距離が変わり、惑星半径にも依存する。**
G の収束因子(C→B で 1.195 対 1.357)に直接効く。

**S-26 [C] 発散判定の倍率 10 が無名。**
`:482` `residual > 10 * bestResidual`。
真に緩慢な収束で残差が一時的に 10 倍跳ねると、
**収束できる配置なのにフォールバックが発動する**(答えは変わらないが 2 倍の費用)。
逆に 10 倍以内でじわじわ発散する配置は検出できない。

**S-27 [C] 仕様書 §7 と実装の細部の不一致。**
`docs/spec/06_降水.md` §7 は
「渦供給(§2) … 保存型では未接続 = **死んでいる**」と正しく書いているが、
**コードのブロックが残っていること**(S-08)と、
**`STORM_DIFFUSION` という繋ぎ口が既にあること**は書かれていない。
また「閾値凝結は渡していない」は書いてあるが、**鉛直輸出**への言及が無い。

**S-28 [C] 全球水収支 −0.0% を「解けている証拠」と読む余地が残っている。**
コード内には明確な警告がある(`:390-393`)が、
仕様書 §7 と較正記録の側にはこの但し書きが無い。
閉包は**不均衡の平均**であって**最大**ではない。

## 4. 最重要 1 件 — S-02 数値拡散が格子解像度を実効拡散係数に変えている

### 何が起きているか(素人向け)

1 次精度の風上差分は、**それ自体が偽物の拡散を持ち込む**ことが数値解析の常識である。
「上流の値をそのまま使う」という近似の誤差が、ちょうど拡散と同じ形をしている。
その大きさは

```
D_num = |u| × Δx / 2
```

で、**格子が粗いほど大きい**。

このモデルの渦拡散 D は 2,977,276 m²/s。同じ土俵で数値拡散を見積もると:

| 格子 | Δx(45°) | Δy | D_num(東西, |u|=8) | D_num(南北, |v|=2) | 物理 D 比(東西) |
| --- | --- | --- | --- | --- | --- |
| 1° | 78.7 km | 111.3 km | 3.15e5 | 1.11e5 | **10.6%** |
| 2° | 157.4 km | 222.6 km | 6.30e5 | 2.23e5 | **21.2%** |
| 4° | 314.8 km | 445.2 km | 1.26e6 | 4.45e5 | **42.3%** |

赤道では Δx が最大(2° で 222km)、貿易風 6.7 m/s で D_num ≈ 7.4e5 = 25%。

### なぜ重大か

**(1) 隠しパラメータである。** CLAUDE.md 禁止事項:
> 隠しパラメータ(計算に効くのに UI にも仕様書にも無い量)。

格子解像度は「表示の細かさ」として扱われているが、実際には
**実効的な渦拡散係数を 10%〜42% の幅で動かす物理パラメータ**として働いている。
同じ惑星をプレビュー(粗い)と本計算(細かい)で回すと、
降水の分布が変わる。これは EBM で 3 回踏んだ「反復の打切りが答えを決める」型と
同じ構造(数値の都合が物理の答えを決めている)である。

**(2) 渦拡散の掃引の解釈を変える。**
2026-08-16 の掃引は 2° 格子(`docs/探索空間の生存性.json` の `gridResolutionDeg: 2`)で
D を 3.0e6 → 6.0e5 まで振った。数値拡散 ≈ 6.3e5 を足した**実効値**で読み直すと:

```
名目 D    3.0e6   2.4e6   1.8e6   1.2e6   6.0e5
実効 D≈   3.6e6   3.0e6   2.4e6   1.8e6   1.2e6   ← 変化幅は 5 倍ではなく 3 倍
1% 分位     64      55      45      33      21
```

**最下端では物理拡散と数値拡散がほぼ同じ大きさ**であり、
「D を 5 分の 1 にしても輸送は収束する / 分布が観測へ近づく」という結論は、
実際には「3 分の 1 にしたら」の話だった可能性が高い。
今後「拡散の変調(緯度・季節)で分布の両端を直す」段へ進むとき、
**変調の下限が数値拡散の床に当たって効かない**という失敗が起こりうる。

**(3) 検出する仕組みが無い。**
唯一の解像度テスト(S-03)は 3 重に盲目で、これを検出できない。
較正(2°)と検証(1°)で格子が違うなら、**較正が選んだ D は検証の格子では
最適でない**ことになる。

### 確かめ方(コードを触らずに測れる)

事前登録を書いてから、以下を測る。予測は**測る前に固定**すること。

1. **D 固定・格子だけを振る**: D = 2.977e6 のまま 1°/2°/4° で回し、
   降水の 1%/50%/99% 分位と分布誤差、および `condRateG`・`waterMm` の
   面積重み統計を比べる。
   **予測**: 粗いほど 1% 分位が上がり 99% 分位が下がる(= 分布が中央へ寄る)。
   4° と 1° の 1% 分位の差が 10mm を超えれば S-02 は成立。
2. **相殺実験**: 2° で D = 2.977e6 と、1° で D = 2.977e6 + 3.2e5(数値拡散の差)を
   比べる。**予測**: 分布統計が 1° の素の走りより 2° に近づく。
   近づけば、格子差の主因が数値拡散であることの直接の証拠になる。
3. 既存の道具で足りる: `scripts/sweep_eddy_diffusivity.ts` に格子指定があれば
   そのまま、無ければ格子を変えて 2 回走らせる。**新規コードは要らない。**

### 直し方の候補(採否は測ってから)

- **(a) 高次の風上(2 次 TVD / MUSCL + 制限関数)**。
  数値拡散を 1 桁下げられるが、非負性を保つ制限関数が要る。
  行方向の線緩和(三重対角)が使えなくなるので、解法の作り直しになる。費用大。
- **(b) 数値拡散を明示的に差し引く**。
  `D_eff = D_target − |u|Δx/2` を面ごとに引く。**負にならないよう clamp が要る**ので
  粗い格子では引ききれない。安価だが対症療法。
- **(c) 何もしないが記録する**。
  D の較正値に「その格子での実効値」を併記し、格子を変えたら測り直す規約にする。
  **最低限これは今日できる。** `docs/較正記録.md` と spec §7 へ
  「D は名目値であり、実効値は格子解像度に依存する」と明記すれば、
  隠しパラメータの条件(仕様書に無い)は外れる。

**推奨は (c) を即座に、(a) は「拡散を下げて移流で補う」路線が
本当に必要になってから。** 2026-08-17 の確定事項
「C→B の主因は G(沈降)であって W ではない」に照らせば、
**輸送の数値精度に手を入れる前に G の沈降緩和を直すほうが利得が大きい**。
ただし S-02 は**測るだけなら安く、記録するだけなら今日できる**ので、
順序を待つ理由が無い。
