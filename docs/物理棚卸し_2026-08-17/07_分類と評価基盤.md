## 1. ケッペン分類器(Step 7)

### 1-1. 実装の位置と方針

`src/sim/step07_koppen.ts`(全 115 行)。Peel et al. 2007 / Beck et al. 2023 の
標準閾値をそのまま実装する。**緯度帯・海岸側などの地理決め打ちルールは持たない**
(冒頭 1〜4 行に明記。教訓 §1 の地理中立)。

- `computeKoppen`(11〜36 行): 陸セルだけを走査し、月別気温 `t[12]`・月別降水 `p[12]` を
  作って 1 セルずつ `classifyKoppenCell` に渡す。海(`landMask` が偽)は id 0 のまま。
- 半球判定は行の緯度のみ(22 行 `latDegOfRow(grid,row) >= 0`)。

### 1-2. 判定規則(行番号つき)

月の原点は**北半球の冬至始まり**(月 0 = 冬至の月)。

| 順 | 行 | 判定 | 内容 |
| --- | --- | --- | --- |
| 前処理 | 43〜46 | 集計 | `mat`=年平均気温、`map`=年降水、`tHot`=最暖月、`tCold`=最寒月 |
| 前処理 | 48〜51 | 季節 | 夏半年 = 北半球なら月 3〜8、南半球なら月 9〜2。`pSummer`/`pWinter` を合計 |
| ① | 53〜64 | **B 乾燥**(最初に判定) | 下記 |
| ② | 66〜69 | **E 寒帯** | `tHot < 10` → `tHot > 0` なら ET、そうでなければ EF |
| ③ | 71〜77 | **A 熱帯** | `tCold >= 18`。最少月降水 `pDry >= 60`→Af、`pDry >= 100 − map/25`→Am、他は Aw |
| ④ | 79〜80 | **C / D** | `tCold > 0` なら C、そうでなければ D |
| ⑤ | 81〜96 | 第 2 文字 | s/w/f。下記 |
| ⑥ | 97〜102 | 第 3 文字 | a/b/c/d。下記 |
| ⑦ | 105〜106 | 落とし穴処理 | Csd など体系に無い組合せは `群+第2文字+'c'` に落とす |

**B の乾燥閾値**(53〜64 行)

```
pThreshBase = 2·mat + 14                     （既定）
              2·mat + 28   （夏雨型: pSummer ≥ 0.7·map）
              2·mat        （冬雨型: pWinter ≥ 0.7·map）
pThresh = max(0, pThreshBase) × 10   [mm/年]

map < pThresh          → B
  map < pThresh/2 → BW、それ以外 → BS
  mat ≥ 18 → h、それ未満 → k
```

`pThresh > 0` の条件があるので、`2·mat + 14 ≤ 0`(≒ 年平均 −7°C 以下)の
寒冷地では B 判定そのものが起きない。**B は年平均気温に強く依存する**ため、
気温の失敗が「乾燥の失敗」に化ける(→ パタゴニアのゲートで実際に起きている。§3-4)。

**第 2 文字**(81〜96 行)

```
sCond = (夏の最少月降水 < 40) かつ (夏の最少月 < 冬の最多月 / 3)
wCond = (冬の最少月降水 < 夏の最多月 / 10)
両方成立 → pSummer > pWinter ? 'w' : 's'
sCond のみ → 's' / wCond のみ → 'w' / どちらも不成立 → 'f'
```

**第 3 文字**(97〜102 行)

```
tHot ≥ 22                       → 'a'
10°C 以上の月が 4 か月以上       → 'b'
D 群かつ tCold < −38            → 'd'
それ以外                        → 'c'
```

### 1-3. 分類器そのものの検定(物差しの上限)

`tests/unit/sim/koppen_instrument.test.ts` と `scripts/check_koppen_classifier.ts` が、
**Beck が分類に使った当の月別平年値を自分の分類器へ通して Beck の区分図が
再現されるか**を測る。物理を通さずに物差しだけを検査する設計である。

```
大分類 96.44% / 詳細 92.05% / 第 2 文字 95.67%（2026-08-01 実測。退行防止の下限)
```

→ **分類器由来の取りこぼしは大分類で 3.6 ポイント程度**。現在の大分類 74.6% との
差 22 ポイントは分類器ではなく物理の失点である(物差しは疑い済み)。

## 2. 目的関数 v4

事前登録: `docs/事前登録_目的関数v4_ゲートの崖を外し分布形を入れる_2026-08-16.md`
実装: `scripts/optimize_lib.ts` 283〜379 行(`evaluateResult`)。
重みの定義は 230〜243 行(`OBJECTIVE_V3`)・259〜263 行(`OBJECTIVE_V4`)。

### 2-1. 式の全体

```
continuousV3 = 大分類%  +  0.25 × 詳細%
             − 4   × (年平均気温 RMSE      / 観測 SD 18.06°C)
             − 4   × (年較差 RMSE          / 観測 SD 12.86°C)
             − 2   × (気温季節位相 RMSE 日 / 30 日)
             − 3   × (年降水 RMSE          / 観測 SD 773mm)
             − 3   × (最少月降水 RMSE      / 観測 SD 35.31mm)
             − 1.5 × (最多月降水 RMSE      / 観測 SD 125.23mm)
             − 1   × (|陸平均年降水の偏差| / 観測陸平均 794mm)
             − 1   × (ITCZ 線 RMSE 度      / 3 度)

fitness(v4) = continuousV3
            + 1.1 × Σ_17地域 share            ← 面積割合の和(0〜17、連続)
            − 3   × precipQuantileLogErr      ← 年降水の分位 8 点の平均対数誤差
```

**無次元化はすべて観測自身の空間ばらつき(面積重み標準偏差)で割る。**
モデルの現状誤差で割ると成績が動くたびに重みが動き、後から都合よく調整する
余地が残るため(`optimize_lib.ts` 210〜214 行)。

### 2-3. v2 → v3 → v4 の差分

| 版 | 期間 | 内容 |
| --- | --- | --- |
| v2 | 2026-07-31 凍結 | 年平均/年合計のみ。`大分類% + 1.1×ゲート件数 + 0.25×詳細% − 0.35×気温RMSE − 0.004×降水RMSE − 0.02×(陸平均偏差の絶対値)/10 − 0.3×ITCZ`。**季節を一切見ていない** |
| v3 | 2026-08-02 事前登録 | 季節指標 3 つ(年較差・気温位相・最少/最多月)を追加し、全項を観測 SD で無次元化。減点合計が約 6.9 → 約 18.8 へ |

v2・v3 は現在も併記のため計算し続けている(`Scores.fitnessV2` / `fitnessV3`)。

**版をまたいで比べてよい量は `continuousV3`(ゲート項を除いた連続部分)だけ**である
(`optimize_lib.ts` 167〜171 行)。fitness の絶対値は版で意味が違う。

**v4 で崖を外した理由**: v23 の採用を分解すると 大分類 +0.07 / ゲート +1.10 /
詳細 −0.355 で、**他の連続指標は約 −0.031 悪化していた**。「良くなった」のではなく
崖を一つ越えたから採用された点だった。

**ε の訂正(同日)**: 分位の対数誤差の 0 割り回避項を、事前登録の 10mm から **1mm** へ訂正
(`scoring.ts` 553 行 `PRECIP_QUANTILE_EPS_MM`)。観測の 1% 分位が 9mm/年で
ε のほうが大きく、7.1 倍のずれを 3.9 倍に圧縮して**新しく入れた項が測りたい対象を
潰していた**ため。根拠を結果に依存しない事実に置いて訂正した。

### 2-4. 失格(数値的健全性)

`scripts/validate_criteria.ts` の `evaluateNumericalSoundness` を
**validate と較正の両方が同じ関数で呼ぶ**(`optimize_lib.ts` 347〜354 行)。
不合格なら fitness を `UNSOLVED_FITNESS = −1e6` に落とす(**棄却であって減点ではない**)。

見る 5 系統: EBM 線形解の残差(≤1e-3°C)/ EBM の年次ドリフト(≤0.05°C)/
降水の結合反復 / 土壌の周期定常 / 保存型の水蒸気輸送(と virga)の未収束月数。

歴史: 2026-08-14 まで判定は `EBM_SOLVER_STATS.capHits > 0` の 1 行だけで、
**逐次経路(`--parallel 1`)には判定が 1 つも無かった**。未収束は歴史的に成績を
よく見せる方向に働く(残差が許容の 233 倍の解が、収束解より 3.5 点良かった)。

## 4. 較正の仕組み

### 4-1. 探索アルゴリズム(`scripts/optimize.ts`)

**座標降下 + 感度スクリーニング**の 2 相構成。状態は `out/optimize/state<接尾>.json`、
評価ログは `log<接尾>.jsonl`(評価番号の正本はログ側)。

1. **基準線**(411〜432 行): 現在の定数ベクトルを 1 回評価。
   **基準が失格したら即座に例外で止める**(定数ではなく実装か収束予算の問題なので、
   探索を続けても直らない。2026-08-11 に 10 時間を捨てかけた実害から)。
2. **screening 相**(479〜514 行): 全 57 定数を範囲幅の ±8% だけ振り、
   `|fitness − bestFit|` の最大値を感度として記録する。基準は固定なので完全並列可。
3. **descent 相**(516〜624 行): 感度の高い順に座標を選び、範囲幅 × `stepFrac` を ±。
   **1 バッチにつき最良の 1 件だけ採用**(同時採用は相互作用が未検証のため)。
   `stepFrac` は 0.18 から始まり、1 スイープごとに ×0.6(下限 0.04)。
4. **スイープの区切り**(524〜588 行): 感度上位 4 定数へ乱数擾乱(jitter)を 1 回、
   さらに**感度上位 3 定数の対を逆対角に振る対探索**を行う。
   座標降下は谷を渡れないため(陸の熱容量と東西移流結合が実例)。

### 4-2. 停滞打ち切り(401 行、既定 124)

descent 相で最良が 124 評価連続で更新されなければ、時間が残っていても終了。
**screening 相は数えない**(更新しないのが正常な工程だから)。
124 = 探索空間 62 定数 × 2 方向 = スイープ 1 周。過去ログの再生で決めた値
(N=60 では v22 が 0.211 点を損した。N=124 は損失ゼロで 75 評価節約)。

### 4-3. 並列ワーカー

`--parallel N` でワーカープロセス N 本。バッチ幅は `ceil(N/2)` 座標 × 2 方向。
実測で並列 2 の 242 秒/評価 → 並列 4 で実効 98 秒/評価(2.5 倍)。
`--parallel 1` は in-process の逐次経路(こちらにも失格判定を入れてある)。

**行儀のよい停止**: `out/optimize/stop_<run名>` を置くとバッチの切れ目で抜ける
(プロセスを殺すと実行中バッチが失われる)。

### 4-4. 来歴の指紋(92〜111 行、316〜376 行)

`out/optimize/run_<名前>.meta.json` に次の指紋を保存し、再開時に照合する。

```
space     = sha256(JSON.stringify(SPACE)) 先頭 16 桁
objective = sha256(optimize_lib.ts の中身 + scoring.ts の中身) 先頭 16 桁
git       = git rev-parse HEAD
```

`space` か `objective` が一致しなければ **exit 2 で再開を拒否**する。
指摘の元は「コード変更をまたいで再開すると、異なる目的関数の数値が同じログに
混ざり得る」(2026-08-15 の外部監査)。実害は近くまで来ていた
(`westerlyWindMs` を探索空間から外したまま v23 を回していた)。

**設計上の要点**: ソース読取は失敗時に例外にしてある(99 行)。空文字を返すと
指紋が定数になり、目的関数が変わっても一致してしまう = **検査が黙って無効化される**。

**副作用**: 走行中の較正では探索空間を変えられない。死んだ定数の除去も
v24 の終了を待つ必要があった。

関連して `verify_applied.ts` は git commit の不一致でも拒否する。v24 の適用時に
実際に発火し、実測で答えの一致を確認してから採用した。

### 4-5. 探索空間の生存性 CI(`tests/unit/scripts/space_liveness.test.ts`)

動的な生存性測定(全定数 × 2 方向のパイプライン実行、実測 40〜60 分)は CI に

- 測るのは `npx tsx scripts/diag_dead_constants.ts --write`(手動、重い)。

### 4-6. 空間保留(holdout、`scripts/holdout.ts`)

`--holdout-fold N`(0〜4)で区画のセルを目的関数から除外する。

### 7-1. 【最重要】降水の季節位相 — 計算されているのに重みがゼロ

> 分類一致率の分散源を測っていないことになる
> (2026-08-09 の外部レビュー 2 件がそろって指摘)。

基準の `phaseScaleDays = 30`(1 か月ずれればケッペンの季節が 1 つ動く)で
無次元化すると 2.40 で、**現行のどの無次元化誤差より大きい**
(最大は年較差の 0.614)。仮に気温位相と同じ重み 2 を掛ければ **−4.79 点**、
現行の罰則合計 16.05 の 30% に相当する新しい項が立つことになる。

これは単なる抜けではなく、**症状の説明とも直結する**。

- 混同行列の最大の穴は観測 C の 48% を B と誤ること。B の判定は
  夏雨型 / 冬雨型で閾値が `2·mat+28` / `2·mat` と **2 倍違う**(§1-2)。
  つまり**雨季の時期がずれるだけで B の閾値が変わり、C が B に落ちる**。
- 実際 `regionDiagnostics` のアマゾンは年降水比 0.95・最少月 136 対 142 と
  **量はほぼ完全に合っている**のに、月別系列を並べると
  最多月がモデル第 3 月・観測第 4 月、**最少月がモデル第 7 月・観測第 9 月**で、
  乾季の底が約 2 か月ずれている(月の原点差 0.355 か月を差し引いても残る)。
  現行の目的関数はこのずれを 1 点も罰しない。
- ケッペン分類器の自己検定(§1-3)が第 2 文字で 95.67% を出しているので、
  第 2 文字の失点は物差しではなく物理側の位相ずれである。

**やるべきこと**: `precipPhaseRmseDays` を `Scores` へ載せ、
`OBJECTIVE_V5` として重みつきで目的関数に入れる(事前登録が必要な変更)。
入れる前に、既存解での寄与を測って重みを決めること(ε の設計ミスの再発防止)。

### 7-2. 風の場が一切採点されていない

目的関数の 12 項はすべて「気温」「降水」「分類」「ITCZ 線」であり、
**風速・風向を直接測る項が 1 つも無い**。にもかかわらず:

- 2026-08-16〜17 の診断はすべて「移流が足りない」「風の場の定式化が原因」
  に収束している(理想化大陸の東岸湿潤欠落、渦拡散が輸送を代行、
  夏の南風が吹いていない)。
- `constants.ts` の `evapBulkCoef` の注記には
  「**風の場が採点されるようになったら測り直すこと**」と書かれている。
  蒸発は `E = ρ·C_E·|V|·q_s·(1−RH)` で風速に線形なので、
  風の誤差は蒸発の誤差として素通りしている。
- 探索空間に風の定数は `tradeWindMs` 1 件しかない(§6-1)。

**測る量が無いので、風を直す変更の良し悪しを目的関数で判定できない。**
現状は個別の掃引と事前登録で凌いでいるが、較正は風を改善する方向へ動けない。

### 7-3. 地域ゲートの二重計上は解消していない(崖を外しただけ)

v4 が直したのは**崖**であって**二重計上**ではない。
事前登録自身が「全球の大分類・詳細一致率と**同じ結果変数を地域ごとに二重計上**
していて、しかも 50%・10% に崖がある」と書いており、後半だけを直した。

現状の帰結:

- ゲート項 **13.462 点**は fitness 82.831 の **16.3%**。
  その中身は「17 の手選びした地球の地域で、ケッペン分類が当たっているか」であり、
  大分類 74.567 と同じ変数を数え直している。
- **地理中立性の観点**: この 17 地域は地球の緯度経度で決め打ちされている。
  計算層には入っていない(検証側のみ)ので三原則には抵触しないが、
  **目的関数の 16% は地球固有の地理に紐づいている**。
  惑星応答や理想化大陸を報酬にする項は 1 つも無いので、較正の圧力は
  「地球の 17 地域に合わせる」方向にのみ働く。
- **`pass` と `share` が別の量を見ている**。受入基準(§3-7)は
  セル数基準の `pass` で 17/17 を要求するが、目的関数が最大化するのは
  面積重みの `share` である。実例として `mediterranean_cs_present` は
  share 0.278 で `pass` = ○(10% present の基準)、
  `us_southeast_humid` は share 0.496 で `pass` = ✗(過半の基準)。
  **share を最大化しても受入は通らない構図**になっている。
- **ゲートは分類しか見ない**ので、サハラ(share 1.000)が観測の 5.9 倍降っていても
  満点である。「当たっているが物理は外れている」を検出できない。

### 7-4. 南極の扱いは分位項だけで、他の項は素通り

- 分位項は 60°S 以南を除く(`scoring.ts` 771 行)。理由は明記されている。
- **一致率・混同行列・気温/降水 RMSE は南極を含む**。面積重みなので
  セル数 28.3% が面積 9.5% に落ちているとはいえ、
  南極は観測もモデルも一律 EF で**必ず当たる 9.5%** の下駄である。
- `antarctica_ice` ゲートは share 1.000 の固定加点(+1.1)。
  **降水は観測の 2%** しか降っていないのに満点である。
- 南極抜きの成績は `scripts/diag_score_masks.ts` の診断としては存在するが、
  `report.json` の正本欄には無い。**成績を報告するときは南極抜きも併記すべき**
  (メモリの「成績は南極抜きも見る」が report.json に反映されていない)。

### 7-5. 計算されているのに目的関数にも入らず報告だけの指標

| 指標 | 現在値 | なぜ重要か |
| --- | ---: | --- |
| 1 月 / 7 月の気温 RMSE | 6.91 / 4.97°C | 年平均(3.75)の 1.8 倍。**ケッペンの閾値は最寒月・最暖月の絶対値**(`tCold ≥ 18` / `tCold > 0` / `tHot < 10` / `tHot ≥ 22`)で決まるのに、目的関数は年平均と年較差しか見ていない。平均と振幅が合っていても位置がずれれば分類は外れる |
| log1p 年降水の空間相関 | 0.569 | 分位項は**分布の形**を測るが**場所**を測らない。相関だけが「正しい場所に雨が降っているか」を見る量で、それが目的関数に入っていない。0.569 はかなり低い |
| 系統バイアス 11 件 | C→B 5.3pt 等 | 凍結された追跡指標だが目的関数の項ではない |
| 地域降水 6 地域 | ラプラタ 0.29 倍等 | 同上 |

### 7-6. 目的関数が地球以外を報酬にしていない

- **理想化大陸(要件 §6-2)**: 4 判定のうち 1 つしか出ていない
  (内陸乾燥 ○ / 地中海性 △ / 西岸海洋性 ✗ / 東岸湿潤 ✗)。
  目的関数に入っていないので、較正はここを一切改善しない。
- **惑星応答(傾斜・自転・気圧・半径・光度)**: 5 軸とも向きは良好だが、
  判定は置かれていない。地球に合わせ込むほど応答が死ぬ危険を
  目的関数は検出できない。
- **退化条件(要件 §6-3)**: 性質テストが受け持っている(目的関数外)。

### 7-7. その他の穴

- **海上の気候は一切採点されない**(共通陸セルのみ)。降水の 2/3 は海上で起きる。
- **数値的健全性は合否のみ**で、余裕の連続量を測っていない。
  ぎりぎり通る解と余裕のある解が同じ扱いになる。
- **陸平均降水の項が事実上死んでいる**(寄与 0.039)。相対偏差 3.9% しかないため、
  重み 1 でも罰則としてほぼ機能しない。
- **分位項の分位点が両端に寄っていない**。1% と 99% の間の 6 点は比が 0.91〜1.29 で
  ほぼ合っており、平均を取ると端の 6.75 倍が薄まる(8 点平均で 0.408)。
  端を測るのが目的なら、対数分位の等間隔化か端の重み付けを検討すべき。
