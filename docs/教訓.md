# 教訓 — ExoClim-2 / 初代 ExoClim / derle-climate から掘り出した知見

> ExoClim-2(2026-04〜06、126 コミット、ユニット 411 + E2E 109 件で停止)と
> 初代 ExoClim の記録(要件定義書・現状.md・開発ガイド §6・PASTA_COVERAGE.md・
> ファイル図鑑屋レビュー)、および手法の異なる姉妹プロジェクト
> [derle-climate](../../derle-climate/)(2026-07、Python、実データ検証まで到達)
> から抽出した。**ExoClim-3 の設計判断の根拠**であり、作業前に一読すること。

## 1. ExoClim-2 が停止した構造(最重要)

ExoClim-2 は技術的には高い完成度に達していた。5 層アーキテクチャは実際に守られ、
`any` 0・TODO 0、テスト 520 件、UI 磨き(U1〜U20)も完了していた。
それでも停止した。死因は個々のバグではなく、**構造の連鎖**である:

1. **中核が質的だった**。気温は「規格化日射 × 経験係数 350/80」の較正式、
   降水は dry/normal/wet/very_wet の 4 段階ラベル。ケッペン判定は
   ラベル→mm の経験変換表(10/60/120/240)の上に載っていた。
   物理量が実在しないので、出力が実際とずれても**回す物理のつまみが無い**。
2. **物差しが主観だった**。実在地球の地形プリセットも実在ケッペン分布との
   定量比較も最後まで存在せず(`tests/fixtures/` は空のまま)、評価は
   理想化大陸の手本画像に対する subagent の主観採点(70 点満点)だけだった。
   採点は 41→47→49→51 と 1 サイクル +2 点で停滞した。
3. **場当たりの帯域強制ルールが積もった**。出力の穴を「西岸 30-42° を強制 Cs」
   「|lat|<5° を強制 Af」「西岸 45-60° の D 群を強制 Cfb」「BWh 連続帯保証」
   のような地理決め打ちの後処理で埋めた(最終的に約 20 個)。これは
   自ら禁じた「場当たり対応」そのものであり、しかも地球の地理を
   ハードコードするため**系外惑星ツールとしての前提を自壊させる**
   (高傾斜・逆行・低速自転で全部嘘になる)。
4. それでも Dfc が陸地の 35% を占め、Cfb は手本の 1/4 のまま、
   チューニングは収束せず停止した。

**再発防止(ExoClim-3 の三原則)**:

- **定量の中核**: 気温はエネルギー収支モデル、降水は mm/月 の水収支。
  ケッペンは実量に対する教科書判定のみ。緯度帯・海岸側を決め打ちした
  気候帯の強制ルールは**一切書かない**。出力が悪ければ物理定数を直す。
- **客観の物差し**: 実在地球(実在海岸線)を入力に、実在ケッペン分布との
  一致率を自動採点するヘッドレスハーネスを**物理実装より先に**用意する。
  主観採点を一次評価にしない。
- **地理中立**: 計算層のどこにも「地球でこうだから」という座標決め打ちを
  置かない。地球らしさは検証側(フィクスチャと採点)にだけ置く。

## 2. なぜ Pasta 手順の忠実な機械化だけでは足りないか

Pasta の手順は**人間の作画者が判断を挟みながら**使う前提で書かれており、
係数の多く(気温スケール、ラベル→降水量、海岸補正の減衰…)は明示されない。
ExoClim-2 はこの「曖昧さ」を経験係数と後処理で埋め続けて溺れた。
ExoClim-3 では: **段階構成・可視化・用語は Pasta を踏襲**し(これがこの
ツールの个性)、Pasta が定量を示さない場所は**標準的な気候物理**
(エネルギー収支、Clausius-Clapeyron、標準ケッペン閾値)で埋める。
「Pasta に書いてないから経験係数」ではなく「Pasta に書いてないから物理」。

## 3. 引き継ぐべき資産(ExoClim-2 で実証済みの設計)

- **5 層構造**: ドメイン → 計算(純粋関数) → ワーカー → ストア → UI。
  依存は一方向。UI はストアのみ購読。実際に守られ、効果があった。
- **パイプラインキャッシュ**: 各ステップのキャッシュキーに**上流出力の参照
  そのもの**を含める設計(`PipelineCache` + `getOrCompute`)。上流不変なら
  参照同一 → 下流ヒットが連鎖する。部分再計算の中核として優秀。
- **ブリッジの二実装 DI**: テストは直接実行、本番は Worker。ストアは
  インターフェースにのみ依存。
- **single-in-flight + replay-latest**: 実行中は 1 本、完了時に
  `getState()` を読み直して最新入力で再実行(古いクロージャを掴まない)。
- **経度循環描画**: 正規化 + 3 オフセット描画 + `dx > W/2` での折線分割。
- **決定性規約**: 乱数は種子必須、`Object.is` 語義の deepEqual、
  浮動小数厳密比較。
- ヘッドレス検証・理想化大陸・地球プリセットという検証 3 段構えの**構想**
  (-2 では構想止まりだった。-3 では最初に実装する)。

## 4. ファイル図鑑屋レビュー(2026-06-14)の指摘 — 初日から組み込む

外部レビューが ExoClim-2 に残した改善点。-3 では設計段階から反映する:

- **F3 取込値の検証**: 設定 JSON 取込は型 + 値域の全項目検証を通し、
  不正項目は落として既定値を残し、利用者に通知する。`1e999`(JSON.parse で
  Infinity 化)や文字列混入をシミュレーションに流さない。
- **F1 陳腐化ガード**: ワーカー応答に要求 id を付け、最新要求以外の
  結果は捨てる(ワーカーが非同期化しても壊れない契約にする)。
- **F5 全キャッシュヒット時の再クローン回避**: 変化なしなら
  `allCached` 通知だけ返し、前回出力を再利用する。
- **F4 ホバーで全再描画しない**: ハイライトは別レイヤ(透明 canvas)に描く。
- **F6 巨大描画関数の禁止**: 描画は層別モジュール + 単一の layers
  オブジェクト渡し。23 個の位置引数のような関数を作らない。
- **F7** スナップショット項目は `satisfies` で型ずれを検出する。

## 5. 開発ガイド §6 教訓カタログからの持ち越し(実装の落とし穴)

- **線形の日射→気温変換は極夜極昼で破綻する**(-2 §6.1.2)。極昼の過剰日射が
  そのまま +25°C になり雪氷が消えた。→ -3 ではエネルギー収支モデル
  (熱容量 + 放射冷却)で根本解決する。この教訓が EBM 採用の直接の根拠。
- **雪氷フィードバック反復で同一セルを多重冷却しない**(-2 §6.1.3)。
  新規凍結セルにのみ効果を適用し、新規ゼロで打ち切る。
  → EBM では albedo が温度の関数になるため構造的に消える。
- **-0 と `toBe(0)`**(-2 §6.1.1): 物理量の 0 判定は
  `toBeCloseTo(0, n)` か `Math.abs` を使う。負係数の積は `-0` を返す。
- **オーバーレイ要素は必ず 3 オフセットで描く**(-2 §6.2.2)。ラベルだけ
  単一オフセット、のような例外を作らない。間引き(cull)は原則入れない。
  入れるなら余白 ≥ サンプル間隔。
- **計算層出力を変えたら UI が実際に消費しているか grep で確認**(-2 §6.3.1)。
  モデル更新と描画更新が独立に進み、UI 側の古い独自実装が残った実例あり。
  描画関数の引数に計算出力を明示的に取らせる設計で構造的に防ぐ。
- **Canvas 指紋テストは感度を疑う**(-2 §6.3.2)。粗いサンプリング指紋は
  重畳描画の増加で差分を検出できなくなる。差分が大きく出る方向の操作で
  テストを書き、重要箇所は特定ピクセル検査を併用。
- **ステップ追加でパイプライン所要時間が伸びると既存 E2E の待機が壊れる**
  (-2 §6.2.1)。固定待機ではなく「計算完了」を UI 状態で待つ。

## 6. 初代 ExoClim(第 1 世代)の統治面の教訓

- **隠しパラメータ禁止**: 計算に効くのに UI からも文書からも見えない量が
  蔓延し、挙動の説明可能性が崩壊した。→ 利用者パラメータは全て UI へ。
  モデル定数は仕様書に根拠つきで明記し、点検ビューから読める形にする。
- **飾りスライダー禁止**: UI にあるのに計算に効かない操作子は信頼を壊す。
- **モジュール聖域化禁止**: 「触ってはいけないファイル」を作らない。
- **一次資料への準拠が薄いままの独自実装**が仕様との乖離を生んだ。
  実装には仕様書(docs/spec/)の節番号を引用する。

## 7. 開発プロセスの教訓(-2 の運用から)

- **-2 の重装プロセスは今の開発体制には過剰**。着手前の教訓引用義務、
  コミット毎の 現状.md/実装済み.md 二重更新(実装済み.md は 407KB まで肥大)
  は、監督付き・小刻み前提の運用だった。-3 では git 履歴 + 本文書群に集約し、
  儀式は課さない。ただし**根本原因主義**(場当たり修正禁止)と
  **仕様引用**(実装に spec 節番号)と**教訓の追記**は維持する。
- **調整つまみを利用者スライダーにしない**。-2 は「UI 未露出パラメータ禁止」
  を較正係数にまで適用して 46 スライダーに膨張し、上級モードで隠す羽目に
  なった。利用者パラメータ(惑星の物理量)と、検証で固定するモデル定数を
  区別する。前者は UI、後者は仕様書 + 点検ビュー。
- **視覚出力を自動で確認できる経路を最初に作る**。-2 の開発エージェントは
  自分の出力画像を見られず、ユーザーの目視フィードバック(「カックカク」
  「海流が陸を無視」)に依存した。-3 ではヘッドレス PNG 出力を最初に整備し、
  開発中に自分で画像を確認しながら反復する。

## 8. derle-climate(姉妹プロジェクト)からの知見

出界(創作惑星)の気候を Python + 実データで推定したプロジェクト。手法は
ML 回帰 + 物理ソルバ + 類似地転写 + スラブ GCM の混成で ExoClim とは別物だが、
**「簡易物理は地球のどこで壊れるか」を実測で特定済み**であり、そこが宝である。

### 8.1 検証手法(そのまま輸入する)

- 正解データ: **Beck et al. 2023 Köppen-Geiger v2**(1991-2020、1°、CC BY 4.0)
  との全球混同行列。大分類と詳細分類の両方の面積重み付き一致率、Macro F1、
  気候境界の平均距離、月別気温・降水 RMSE。
- **地域ゲート**: 全球集計だけでは自己欺瞞になる。「サハラが乾燥優勢」
  「ロシアが D 群優勢」「米南東部が湿潤」等の重点地域の合否を列挙し、
  **全部通って初めて採用**とする(derle は v10 で大分類 61.6% でも REJECTED)。
- **地域別の手書き補正なしで達成する**ことを受入条件に明記(derle も同方針)。
- データは ../derle-climate/data/processed/ に整備済み(ETOPO 2022 1° CC0、
  Beck ラスター + 月別平年値 CC BY 4.0)。scripts/build_earth_fixtures.py で
  ExoClim-3 のフィクスチャに変換する。出所・SHA256 は derle 側 manifest.json。

### 8.2 簡易物理モデルの系統バイアス(derle 実測、v10 時点)

ExoClim-3 の降水・気温モデルが同じ穴を踏まないための先回りリスト:

- **シベリア・ロシアを乾燥化しすぎ**(BC/TC のはずが CS/CD に)。原因は
  偏西風の長距離水蒸気輸送・陸上再蒸発(水分再循環)の弱さ。冷帯の湿潤
  (Df)は「海からの直接輸送」だけでは説明できない。
- **地中海性気候(夏乾・冬雨)が出ない**。冬季ストームトラック(寒候期に
  中緯度西岸へ雨を運ぶ)を季節の位相つきで持たないと Cs は再現不能。
- **アラビア・西サハラを湿潤化しすぎ**、**豪州内陸を湿潤化しすぎ**。
  亜熱帯高圧帯の沈降乾燥が弱いか、海からの湿気侵入を許しすぎ。
- **東アジア・米南東部の湿潤(Cfa)が出ない**。亜熱帯乾燥帯と東岸モンスーン
  湿潤の切り分けには、大陸東岸で夏に海から吹き込む流れが必要。
- **コンゴ・アマゾンの降水不足**(熱帯収束帯の陸上降水 + 再蒸発)。
- **高緯度の絶対気温は簡易モデル間で恒久係争**(60-70°N で観測 -6.4°C に
  対し各モデル -6.7〜-16.7°C)。海洋熱輸送を含む拡散・移流の較正が肝。
  ExoClim-3 は観測帯状気温プロファイル(月別)への直接較正で正面から挑む。
- **海洋熱輸送を持たないモデルは西欧で必ず失敗する**(メキシコ湾流の不在。
  derle の GCM 不採用の決定打)。暖流の熱輸送 → 気温への経路を最初から持つこと。
- 粗い擬似標高は沿岸都市を高山扱いにする → 実標高(ETOPO)を使う。

### 8.3 プロセスの知見

- **受入基準は結果を見る前に固定する**(derle は事前登録 + 採用規則を運用)。
  結果に合わせて基準を緩めた時点でチューニング地獄が再発する。
- **全球一致率と重点地域ゲートは別物**。どちらか一方では欺瞞が入る。
- 独立レビュー(別 AI・別会話)は過大主張の検出に有効だった。
- 較正に使ってよいのは物理特徴だけ。地域ラベル・観測点座標・正解区分を
  モデル内部に持ち込まない(derle v10 の「空間ホールドアウト校正」方針)。

## 9. ExoClim-3 自身の教訓(開発中に踏んだもの)

- **計算層(src/sim/)はブラウザの Worker でも動く前提で書く**。`process.env` 等の
  Node 専用 API を直接参照すると Worker が「process is not defined」で全滅する。
  診断フラグは `typeof process !== 'undefined'` でガードする(2026-07-30 実害)。
- **Playwright の `reuseExistingServer: true` は「古いビルドの検証」事故を招く**。
  残骸プレビューサーバが旧 dist を配信し続け、壊れた新ビルドでも E2E が緑に
  なった。自前起動(false)に固定し、E2E には「エラーバッジ不在」の断言を入れる。
- **`vite preview` はビルドしない — 「残骸ビルド」も別に潰す**(2026-07-30 実害)。
  reuseExistingServer: false にしても、webServer が `npm run preview` だけだと
  数コミット前の dist を延々検証し続ける(新 UI が「無い」のに 3 本緑のまま)。
  webServer.command は `npm run build && npm run preview` にする。UI 変更の E2E は
  「新要素が存在する」断言を先に書いて赤→緑を確認すると残骸に気づける。
- **解像度を変えるものは距離基準で書く**(セル数・ステップ数の定数は 2°/1°/0.5° で
  挙動が変わる)。供給の線積分重み・追跡ステップ上限・走査幅で 3 連発した。
- **較正の走行中はコミットしない — 成果物の来歴が壊れる**(2026-08-01 実害)。
  v6ebm の較正は ad1d190 で開始したが、走行中に別作業の 2 コミットが入り、
  ワーカーは途中から違うコードを評価していた。結果、較正の自己採点
  (地域ゲート 14)が完走後の HEAD で再現せず(13)、9 時間ぶんの探索が
  丸ごと無効になった。`run_*.meta.json` の `gitCommit` と検証時の HEAD が
  一致するかを**採否判定の前に必ず確かめる**。並行作業がある場合は
  別ワークツリー(`git worktree add`)で行い、本体の HEAD を動かさない。
- **較正が「改善なし」で頭打ちなら、それ自体が情報**。v6ebm は 1,000 回以上
  評価して 1 定数しか動かさず、その 1 定数は検証スコアを一切変えなかった。
  探索を延長するより、構造(定式化)の欠陥を疑って実測診断へ回すほうが速い。
- **採点の分位を実測と突き合わせる — 平均だけ見ると壊れ方を見落とす**
  (2026-08-01)。陸平均年降水はモデル 781mm / 実測 794mm と一致していたのに、
  分位で見ると p10 が 2mm 対 39mm、p25 が 30mm 対 140mm で乾側だけ壊れており、
  p75・p90 は 10% 以内で合っていた。平均の一致は「湿側の過剰が乾側の不足を
  埋めていた」だけだった。RMSE も同様に壊れ方の向きを隠す。
- **反復回数の決め打ちは隠しパラメータになる。「回数を増やしたら答えが変わるか」を
  必ず測る**(2026-08-01)。EBM 内側の Gauss-Seidel を 8 回で打ち切っていたが、
  16・32・64・128・256 と増やすと気温場が面積平均で計 2.1°C 動き、大分類一致率が
  74.32 → 71.93 へ**単調に悪化**した。反復自体は健全に収束しており(差は
  1.25 → 0.55 → 0.24 → 0.07 → 0.015°C と幾何級数的に縮む)、問題は
  **収束解のほうが成績が悪い**こと。つまり拡散・移流係数が打ち切り誤差を
  打ち消す向きに較正されており、成績 74.32 のうち 2.4pt は物理ではなく
  数値誤差への当てはめだった。`GS_SWEEPS = 8` は constants.ts にも spec にも
  無いベタ書き定数で、CLAUDE.md が禁じる隠しパラメータそのもの。
  **反復は残差基準で止める**(許容差は数値誤差のものとして結果を見る前に固定し、
  spec に書く)。詳細は [実験記録_EBM赤黒順序_2026-08-01.md](実験記録_EBM赤黒順序_2026-08-01.md)。
- **未収束の反復では「順序」が答えに残る。収束させれば消える**(同上)。
  Gauss-Seidel を GPU 向けに赤黒順序へ変える実験は、8 スイープでは
  気温 RMSE +0.061°C(事前登録した許容 +0.050 超)で棄却された。
  しかし線形系の解は一意なので、収束させれば順序差は消える。
  **収束させることが、隠しパラメータの除去と GPU 並列化の両方を同時に開く**。
  「速くするための妥協」に見えたものが、実は正しさの側の要求だった。
- **「対称化した」と書いたら、両側から計算して一致するか確かめる**(2026-08-02)。
  EBM は「P2-2: 界面伝導度を厳密対称にする」と謳っていたが、対称化していたのは
  実効拡散係数だけで、ハドレー増強は**自セルの緯度**で評価していた。増強は緯度で
  変わるので、30° 付近の 2° 界面で伝導度が **8.7%** 食い違い、亜熱帯に系統的な
  エネルギーの湧き出し/吸い込みができていた。面の量は**面で一意に定義**すること
  (両側セルの実効係数の平均)。体積規格化(cos で割る)はセルごとに違って正しい —
  「非対称なもの」と「非対称であってはならないもの」を分けて考える。
- **地形データの「陸」は出所の定義を確認する**(2026-08-02、利用者の指摘)。
  ETOPO 2022 の **surface** は氷の**上面**標高なので、「標高 > 0」で陸を作ると
  南極の棚氷(浮氷。ロス 41m・ロンネ 63m)が陸に入る。実測でモデルの南極が
  Beck より 630 セル広く、逆向きのずれは 0 だった。Natural Earth の棚氷ポリゴンで
  578 セルを海へ戻して fit +0.44。**採点対象外の領域の誤りでも、物理を通じて
  採点対象に効く**(南緯 60-90° の気温 −0.35°C が北へ伝わる)。
- **「初期値に依らない」は書く前に初期値を変えて確かめる**(2026-08-02)。
  土壌バケツの周期定常解は陸セルの **11.15% で年間縮小率がちょうど 1** で、
  真に縮退している(解の連続族)。空回し年数をいくら増やしても閉じない。
  ただし縮退するのは「ET が貯水に依らなくなる」領域なので、**下流へ渡る ET は
  初期値に依らない**(面積平均の相対差 0.00%)。
  詳細: [実験記録_土壌の縮退_2026-08-01.md](実験記録_土壌の縮退_2026-08-01.md)。
- **子プロセスを産む長時間ジョブは、止めたつもりで止まっていない**(2026-08-02 実害)。
  較正を 2 度止めたが、殺したのは親だけで `optimize_worker` の子 8 個が
  生き残り、GPU と CPU を数時間食い続けた。評価速度が 85 秒 → 240 秒に落ちて
  いたのに、原因に気付くまで時間がかかった。`pkill -f` は Windows では
  当てにならない。**実行名をコマンドラインに目印として残し**、
  `scripts/stop_optimize.ps1 -Run <名前>` で親子まとめて狙い撃ちする。
  なお目印なしで一括停止すると、動かしたい較正まで巻き込む(これも踏んだ)。
- **「増やしても変わらない」を言う前に、増えているのが何かを確かめる**
  (2026-08-02、自分で踏んだ)。EBM の積分年数を 4/6/8/12/16 と変えて結果が
  ビット一致したので「周期定常に到達している」と結論した。**誤り**だった。
  `spinupSteps = (ebmYears − 2)` なので、どの年数でも**全熱容量で回るのは
  常に末尾 2 年**で、増えるのは熱容量 1/16 の加速期だけ。加速期は時定数が
  1/16 なので速く落ち着き、当然どれも同じ状態から最後の 2 年に入る。
  検証したかったのは「2 年で緩和が足りるか」なのに、それは一切動かしていなかった。
  **収束を主張する実験は、動かした量が本当に律速の量かを確かめる。**
- **状態変数が二役を担っていないか確かめてから最適化する**(2026-08-02)。
  EBM の反復を速くしようと「前ステップからの線形外挿」を初期推定に入れたら
  気温 RMSE が 3000°C に発散した。原因は `temp` が
  **(a) 右辺 (C/dt)·Tⁿ を作るための前ステップ温度**と
  **(b) 反復の作業変数**を兼ねていたこと。右辺を作る前に書き換えたので、
  初期推定ではなく**物理そのもの**を変えていた。右辺の後へ移して正常化。
  なお外挿の効果は残差 1.7e-5 → 1.3e-5 と 25% しかなく、**採用しなかった**
  (収束を律速しているのは初期推定の質ではなく空間方向の情報伝播)。
- **外部レビューは「問題なし」の列挙も受け取る**(2026-08-02)。Codex の GPU 移植
  レビューで 5 件の指摘を得たが、同時に「同期は WebGPU の仕様上追加バリア不要」
  「f32 の丸めは 1e-3°C の閾値に対し 5e-6°C で十分」という確認も得られた。
  **異機種 GPU 間のビット一致は保証されない**(WGSL は丸め方向を固定せず、
  cos/exp/除算に許容誤差がある)ことも判明 — 同一アダプタでの再現性とは分ける。
